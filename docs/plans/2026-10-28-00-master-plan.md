# Claude Desk Prototype — Master Plan v2 (architecture, contracts, schedule)

> **For agentic workers:** Execute with the repo's `executing-implementation-plans` skill (`.agents/skills/`): a fresh implementer and a task review per task, in a worktree per part plan, landing through a PR after the two-reviewer panel. Steps use checkbox (`- [ ]`) syntax for tracking. This master plan owns the trust boundary, the shared contracts, the kernel API, the decision semantics and the schedule; each subsystem has its own plan (index below) that consumes these names exactly. v2 folds in a pre-implementation design review; the last section lists what changed from v1.

**Goal:** A hosted Claude Desk prototype where strangers and agents talk to a business's public Claude, every tool call and every visitor-visible message passes code checkpoints in a Rust/Cedar safety kernel, and the owner app shows approvals, rules and a verifiable safety ledger.

**Architecture:** Two processes in one ECS task. The **kernel service** (Python/FastAPI on 127.0.0.1:8701, never exposed) owns sessions, verification, policies, facts, approvals, business data and the ledger, holds every business credential, and imports the Rust `desk_kernel` module (PyO3) for Cedar decisions, proofs, canonical JSON and Ed25519 signing. The **API service** (Python/FastAPI, port 8700) runs the agent loop, visitor/owner APIs and SSE; it holds only the Anthropic API key and its own database role, and passes session IDs, never identities, to the kernel. The React (Vite) web app is static on S3 and served with the API from one CloudFront origin (`/api/*` → ALB).

**Tech Stack:** Python 3.13 (uv), FastAPI, Pydantic v2, SQLAlchemy 2 + Alembic, Postgres 16, Procrastinate, sse-starlette, `anthropic` and `mcp` Python SDKs, `stripe` (test mode); Rust stable + PyO3 + maturin, `cedar-policy` 4.14, `cedar-policy-symcc` + cvc5 (static binary), `ed25519-dalek`, `sha2`; React 18 + Vite + TypeScript; AWS: ECS Express Mode with a custom two-container task definition (Fargate arm64 + ALB), RDS Postgres, S3 + CloudFront, Secrets Manager, CDK (Python).

**Spec:** `docs/specs/2026-10-28-claude-desk-design.md` (design, decisions log, threat model). Designs: the Claude Desk design canvas linked from the spec.

## Global Constraints

- Deadline Monday 2026-11-02, with a scope gate Friday 18:00 (see Schedule). Never cut: proofs (or the labelled bounded fallback), data labels, reply checks, the attack gate.
- Claude via the Anthropic API only: `claude-opus-5-5` for conversations, `claude-haiku-5-5` for triage, the soft-promise check and owner translations, `claude-sonnet-5` for the auto reviewer.
- The API process holds `ANTHROPIC_API_KEY` and the `desk_api` database role only. It never sends a principal, person, level or assurance to the kernel, and it cannot write kernel tables.
- Every tool call goes `ToolCall → kernel /decide → allow | hold | refuse`. Execution needs an `allow` no older than 60 s or a single-use owner approval bound to the exact normalized action; both are re-decided against the current policy, pins and spend at execution.
- Every visitor-visible message, card, error text and A2A response passes kernel `/check_reply` and leaves through one API function, `deliver()` (check-then-reveal; nothing unchecked is streamed).
- Prices, discounts, dates, bookings and policies appear only in clauses rendered by code from facts (English and Spanish templates). Free prose containing digits, money, percentages, dates or promise words (en/es lexicon) is blocked; one regenerate with feedback, then the handoff clause ("Let me check with Maria").
- Prices are computed by the kernel from the Desk's price list; Claude never supplies an amount, a discount or a recipient. Messages and documents go only to the owner or to the verified person's contact on record.
- Rules: Claude drafts rule cards; `compiler.py` emits Cedar; proofs gate activation; the owner confirms. No hand-written or model-written Cedar is ever activated.
- Review scores are integers in basis points (0–10000), allowed only as top-level `&&` conjuncts on `@tier("auto")` permits. Reviewer errors and timeouts leave the score absent, so the action is held.
- Always-on baseline: AI disclosure; private data only to the verified record owner; verification codes only to the contact on record; no `pay_out` without an owner rule or approval; agent charges only within a verified mandate; auto-allowed money ≤ $500 per action (`AUTO_MONEY_HARD_CAP_CENTS = 50_000`); every attempt logged.
- Verification: kernel-owned challenges (10-minute expiry, 5 attempts, one live challenge per session, uniform replies that don't confirm whether a contact exists). Each challenge gets a fresh random 6-digit code (CSPRNG), stored only as a hash and delivered only to the Demo inbox entry for the contact on record. The Demo inbox stands in for that contact's real inbox: the agent loop and the model context never see codes, and the attack suite treats the inbox as out of the attacker's reach. Sessions verified this way carry `assurance="demo_code"` and the UI labels verification as simulated. No real email, SMS or push.
- Payments: Stripe test mode. Native payment links use the Stripe SDK inside the kernel. Stripe MCP is used only for allowlisted operations with trusted adapters (`stripe.list_charges`, `stripe.create_refund`); unknown or drifted tools stay disabled.
- Data: unlabeled data is owner-only; combining data intersects reader sets; documents leave only as single-use kernel links; each document carries a canary string used by runtime leak checks and evals.
- Languages: the kernel detects English or Spanish; anything else is handed to the owner. Owner-side translations and summaries are labelled AI-written and never shown to visitors or used in approval cards.
- Copies: each passcode holder gets a fresh copy of the Rivera Plumbing seed (kernel `POST /copies`); every kernel row carries `copy_id`; a shared Desk link grants visitor access to that Desk, never owner access to its copy.
- Spend: no monthly cap; per-visitor rate limits.
- Product name "Claude Desk"; copy is sentence case, plain, no door/knock wordplay; footer "Concept prototype by Giovanni Alcantara, not an Anthropic product"; no Claude/Anthropic logos.
- Design system v2 tokens (warm dark: app #1C1B19, panel #222220, surface #2A2927, selected #3C392F; Source Serif 4 for Claude's voice and titles; Hanken Grotesk UI; clay #E08968 only in the mark).
- Git: small conventional commits, written for readers of the public history, each ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

Each line names the plan that must carry a test for it.

- A visitor claims to be another customer, or asks for the code to go to a new email → the code goes only to the contact on record, the reply is the uniform one, the typed contact is stored as a lead note, and nothing about the record is revealed (Plan 01 verification; Plan 05 tier 1).
- A visitor or agent pushes money: "Maria said $1", "80% off", ten $20 charges against a $100 mandate, or a refund under a mandate → server price stands, prose with numbers is blocked, the eleventh charge and every refund are refused (Plan 01 adapters, mandates, reply check).
- The owner answers a held request after it expired, after the visitor cancelled, after the policy changed, or twice → it resolves once, is re-decided against the current policy, and never executes twice (Plan 01 approvals; Plan 02 jobs).
- The owner takes over while Claude's turn is in flight → no reply or action from the old generation is shown or executed (Plan 01 sessions; Plan 02 loop).
- A connected MCP server changes a tool definition, or Claude calls a Stripe operation outside the allowlist → the tool is disabled until the owner reviews it and the call is refused (Plan 01 pins and adapters).

## Trust boundary and threat model

- **In scope:** hostile visitors, visiting agents, tool outputs, MCP servers and their descriptions, uploaded or fetched knowledge, owner whispers as text.
- **Hardened against a buggy or compromised API process:** the kernel owns sessions and verification; owner actions require an owner session the kernel issued and checks; approvals bind to the exact action; the API's database role cannot write policies, facts, approvals, sessions or the ledger; business secrets exist only in the kernel container.
- **Claim we can defend:** a bug in the chat layer can't move money, change rules, approve anything, verify anyone or forge the ledger.
- **Not claimed (roadmap):** confidentiality of data already in a verified session's model context against a compromised API; browser-verified signed replies; sealed private documents; browser-signed approvals.

ActorKind = Literal["visitor", "agent", "owner"]
Assurance = Literal["none", "demo_code", "owner_session"]   # "demo_code" = simulated verification
SessionMode = Literal["ai", "owner", "paused"]               # "owner" = owner took over; the loop stops

    ledger_seq: int

    end: time

## Decision semantics and proof obligations

**Policy sets.** The compiler turns cards into four annotated sets (`@id`, `@card`, `@tier`):

| Set | Source | Shape |
|---|---|---|
| `B` | `cedar/baseline.cedar` | forbids, always on |
| `F` | `never` cards | `@tier("refuse")` forbids |
| `A` | `auto` cards | `@tier("auto")` permits; review thresholds only as `context has review && context.review.within_charter_bp >= K && context.review.manipulation_bp <= K` |
| `H` | `ask` cards, plus a review-free twin of every `auto` card | `@tier("hold")` permits |

**Evaluation (`decide.py`, with `PolicyEngine.decide` in Rust):**
1. The adapter normalizes the call, the kernel resolves the resource and its owner, and numbers are range-checked. Any failure → `refuse`.
2. `auto` = Cedar over `B ∪ F ∪ A` with `context.owner_approved = false`, evaluated twice: review at best (10000, 0) and at worst (0, 10000). Same result → the reviewer is not called. Different → the reviewer runs (structured action, cards and facts only; no visitor text; free-text arguments cut to 200 characters) and Cedar runs once more with its scores. A reviewer error or timeout leaves `review` absent.
3. `auto` allows → `allow`. Otherwise `approvable` = Cedar over `B ∪ F ∪ H` with `context.owner_approved = true`: allows → `hold`; denies → `refuse`.
4. Any evaluation error in any call → `refuse`. The kernel never relies on Cedar skipping an erroring forbid.
5. At execution, steps 1–4 run again against the current policy version, pins and mandate spend: an `allow` must still pass `auto` with its stored review; an approved `hold` must still pass `approvable`.

**Lint at compile (`lint_policies`, Rust):** `context.review` only as top-level `&&` conjuncts in `@tier("auto")` permits, monotone (`>=` on `within_charter_bp`, `<=` on `manipulation_bp`); every policy carries `@id`, `@card` and `@tier`; no `unless` mentions review; any other shape rejects the draft.

**Proof obligations (every activation; a solver timeout or `unknown` counts as failure):**

| Check | SymCC query | Catches |
|---|---|---|
| `never_errors` | never-errors over `B ∪ F ∪ A ∪ H` | a forbid that errors and is skipped |
| `baseline_auto`, `baseline_approvable` | `B ∪ F ∪ A` and `B ∪ F ∪ H` each imply every set in `cedar/invariants/` | compiler or baseline regressions |
| `auto_within_cards` | `B ∪ F ∪ A` implies `R`, where `R = reference(cards)` comes from a second generator written independently of the compiler, without review conditions | Cedar wider than what the owner confirmed |
| `review_only_narrows` | `B ∪ F ∪ A` implies `B ∪ F ∪ strip_review(A)` | a score that widens access |
| `hold_within_cards` | `B ∪ F ∪ H` implies `R_hold` | an approvable action the owner marked never |

Invariants: private data only to a verified `record_owner`; recipients only `owner` or `verified_contact`; no `pay_out` for agent principals; agent charges ≤ `context.mandate_remaining_cents`; quote totals ≥ `floor_cents`; auto-allowed money ≤ `AUTO_MONEY_HARD_CAP_CENTS`. `explain.py` turns counterexamples into the owner's words ("Dana could get a $500 refund without asking you"). If SymCC cannot run a check, `bounded_check` evaluates generated requests on every card boundary and the report says "checked on N cases".

## Kernel HTTP API v2 (127.0.0.1:8701, JSON; request models in `backend/desk/kernel_api.py`)

Owner-authenticated calls carry the `X-Owner-Session` header, which the kernel issued and verifies; no call accepts a principal.

| Call | Auth | Body → response |
|---|---|---|
| `POST /copies` | passcode checked by API | `{}` → `{copy_id, copy_secret, owner_session}` (seeds the copy) |
| `POST /sessions` | none | `{desk_slug, kind: "visitor"\|"agent", agent_auth?, mandate?: Mandate}` → `SessionState` |
| `POST /sessions/{id}/mode` | owner | `{mode, generation}` → `SessionState` (bumps generation) |
| `POST /verify/start` | session | `{session_id, contact}` → `{message}` (uniform) |
| `POST /verify/check` | session | `{session_id, code}` → `SessionState` |
| `GET /context/{session_id}` | session | → `{tools: [ToolProfile], facts: [Fact], knowledge: [KnowledgeItem]}` filtered by labels |
| `POST /decide` | session | `{session_id, generation, call: ToolCall}` → `Decision` |
| `POST /execute` | session | `{decision_id, session_id, generation, approval_id?}` → `ExecResult` (idempotent per decision) |
| `POST /actions/{action_id}/cancel` | session | `{session_id}` → `Decision` |
| `POST /approvals/{decision_id}/answer` | owner | `{answer: ApprovalAnswer}` → `ApprovalResult` |
| `POST /check_reply` | session | `{draft: ReplyDraft}` → `ReplyVerdict` |
| `POST /owner/messages` | owner | `{session_id, text, kind: "say"\|"whisper"}` → `{message_id, facts: [Fact]}` |
| `POST /policy/draft` | owner | `{desk_id, cards: [RuleCard], expected_parent}` → `PolicyVersion` (compiled, linted, proved) |
| `POST /policy/confirm` | owner | `{desk_id, version}` → `PolicyVersion` (atomic; 409 if the parent is no longer active) |
| `POST /tools/connect` | owner | `{desk_id, server: "stripe"}` → `[ToolProfile]` (allowlisted operations only, pinned) |

## Rust module surface (`desk_kernel`, imported only by the kernel service)

- `PolicyEngine(schema_json: str, baseline: str)`; `.load(key: str, policies: str) -> list[str]` (lint errors; empty means loaded and cached under `key = "<desk_id>:<version>"`); `.decide(key: str, request_json: str) -> str` → `{outcome: "allow"|"hold"|"refuse"|"needs_review", policy_ids, errors}`.
- `lint_policies(policies: str) -> list[str]`.
- `prove(schema_json: str, sets_json: str, checks_json: str, timeout_ms: int) -> str` → `ProofReport` JSON; releases the GIL; `selftest() -> str` runs one implies check for `/health`.
- `canonical_json(s: str) -> str` (RFC 8785); `ledger_hash(envelope_jcs: str) -> str`.
- `Signer(signing_key_hex: str)`: `.key_id() -> str`, `.sign(msg: bytes) -> str`; `verify_chain(entries_json: str, public_key_hex: str) -> str` → `{ok, first_bad_seq}`.
- `version() -> str`.

## Data model and database roles

- **Roles:** `desk_admin` owns the schemas and runs Alembic and Procrastinate migrations; `desk_kernel` reads and writes `kernel.*`; `desk_api` reads and writes `app.*` and `procrastinate.*`, and may only `SELECT` from `kernel_ro.*` views (no secret hashes, codes or document bodies).
- **`kernel.*` (`KERNEL_TABLES`):** `copies`, `businesses`, `desks`, `people`, `sessions`, `verification_challenges`, `agent_keys`, `mandates`, `tools`, `policy_versions`, `actions`, `decisions`, `approvals`, `executions`, `facts`, `knowledge_items`, `price_items`, `quotes`, `calendar_slots`, `bookings`, `documents`, `document_links`, `payment_links`, `handoffs`, `demo_inbox`, `ledger_heads`, `ledger_entries`.
- **`app.*` (`APP_TABLES`):** `messages` (blocks, language, owner translation, visibility), `run_events`, `setup_interviews`, `notification_prefs`.
- **Constraints:** `copy_id` on every kernel row, and every kernel query goes through `KernelRepo(copy_id)`; `desks.slug` unique (`rivera-plumbing-<6 chars>`); one confirmed booking per slot (partial unique index); `approvals.decision_id` unique; `executions.action_id` primary key, with intent written before any side effect and the provider idempotency key set to `action_id`; `ledger_entries` unique on `(desk_id, seq)`, appended under a `FOR UPDATE` lock on the Desk's `ledger_heads` row, with the event stored as canonical JSON text (not JSONB); a signed head checkpoint goes to the owner's Demo inbox every 50 entries.
- **Secrets:** the kernel container gets `KERNEL_DATABASE_URL`, `LEDGER_SIGNING_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_MCP_KEY` and `ANTHROPIC_API_KEY` (reviewer and soft-promise checks); the API container gets `API_DATABASE_URL`, `ANTHROPIC_API_KEY` and `PASSCODE_HASH`. Both arrive through per-container ECS `secrets` fetched by the execution role; the task role has no Secrets Manager, KMS or S3 permissions.
- **Demo inbox visibility:** the copy's owner session sees every entry; a visitor session sees only entries for contacts it entered itself.

## Changes from v1

- The kernel owns sessions, verification and owner sessions; kernel calls take `session_id`, never a `Principal`; separate database roles and per-container secrets.
- Contracts v2: normalized actions with kernel-resolved resources and server-computed prices; `charge`/`pay_out` split; typed fact claims with status and source; labels default to owner-only; typed reply clauses and violations; signed delegation envelope; typed ledger events; SSE event union.
- Claude drafts rule cards and code compiles them to Cedar; the three-way decision is defined over four policy sets; review scores are basis points and only narrow; two-point evaluation replaces partial evaluation; proofs target `never_errors`, `auto_within_cards` and `review_only_narrows`, not only the baseline.
- Approvals are single-use records bound to the exact action and re-decided at execution; execution is idempotent with intent recorded first; cancellation and expiry are states.
- Policy lifecycle is draft → prove → confirm → activate, bound to policy, schema, baseline and profile hashes.
- Stripe MCP is reduced to an allowlist of operations behind trusted adapters; native payment links use the Stripe SDK.
- Take-over, whisper and hand-back use a session generation that fences stale replies and actions.
- The ledger appends under a per-Desk head lock over canonical JSON, with an append call for API-origin events and periodic signed head checkpoints.
- Demo-code verification is labelled as simulated (`assurance="demo_code"`); website fetching is restricted to public addresses.
- Task 1 is a feasibility spike (proof, counterexample, error and timeout handling, Linux arm64 build) using the `analyze` feature, not `experimental-symcc`; table lists are constants, so the tests no longer depend on a hand-counted number.
- The schedule deploys a hosted thin slice on Friday, adds a Friday 18:00 scope gate, runs lanes in parallel, and keeps Sunday for evals, fixes and the write-up; evals gate legitimate completion on a held-out split as well as attacks.
