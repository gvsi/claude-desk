# Claude Desk Prototype — Plan 07: The About this prototype readers

> **For agentic workers:** Execute with the repo's `executing-implementation-plans` skill (`.agents/skills/`): a fresh implementer and a task review per task, in this plan's worktree, landing through the two PRs in "Landing" after the review panel. Steps use checkbox (`- [ ]`) syntax for tracking. Task 1 builds on `main` as it is; Tasks 2, 3 and 4a build on `main` after PR 1 (the reader's logic, figures and page component, ahead of the web app); Tasks 4b, 5 and 6 build on the web app's run 1 (plan 04, Tasks 1–7) as merged.

**Goal:** Two long-form reading pages inside the prototype, one for the product proposal and one for the capability prediction, opened from an "About this prototype" group in the owner sidebar. Each page is a standalone reader with a back link to the Desk: a centered serif title and one-line summary, a lead figure (the v1 architecture for the proposal, Claude's τ³-Banking scores for the prediction), a numbered contents list, the document in a serif reading column, an author, date and reading-time column, one pull quote, and a card to the other document. The text of both documents lives in the repo as Markdown under `docs/`, so the repo's docs check covers it and a reader of the repo reads the same words.

**Architecture:** Three parts. (1) The two documents as Markdown in `docs/`, shipped docs under the docs check, with HTML comments marking where a figure goes and a relative link from the proposal to the prediction. After Task 1 these files are the source of truth ("Document lifecycle"). (2) A Markdown reader in `web/src/about/` that parses the subset these documents use into typed blocks when its lazily loaded route module first runs (no HTML passes through, no `dangerouslySetInnerHTML`), maps the relative document link to the other page's route, and renders the reader layout and three page-specific figures from design-system tokens and components. Vitest's real-document tests, which CI runs on every push, are the gate that keeps a malformed document out of a deploy; an error boundary keeps a parse error inside `/about/*`. (3) Two static routes, `/about/proposal` and `/about/prediction`, that make no API request and read no session, plus the sidebar's `about` group in the owner shell (the design system's `Sidebar` prop). The owner shell imports only `web/src/about/links.ts`, which holds no document and no parser, and `routes.tsx` reaches `ReaderPage` only through `import()`, so a document that can't be parsed never reaches the app's entry module. They are readable without the passcode, as plan 04's vision pages are, and carry `noindex` (project owner, 2026-10-29), since the repo is still private.

**Tech Stack:** the web app's toolchain as plan 04 pins it (React 18.3.1, TypeScript 6.0.3, Vite 8.3.4, Vitest 5.0.4 with the browser provider, Playwright 1.64.0, `react-router` 7.18.4 with route `lazy`, `axe-core` 4.14.0, `@axe-core/playwright` 4.13.0). Vite's `?raw` import brings the two Markdown files in as strings. No new dependencies: the Markdown subset parser is about 150 lines of our own code with its own tests.

**Spec / master plan:** `docs/specs/2026-10-28-claude-desk-design.md` ("Navigation", "Design system v2 (locked)" and its exceptions, "First visit and hosting"); `docs/plans/2026-10-28-00-master-plan.md` ("Global Constraints", "Schedule, lanes and gates", "Plan index"); the web app plan (plan 04: Global Constraints, Task 1's `expectScreenBasics` and guards, Task 4's owner shell, Task 17's vision pages and route checks); the deploy and docs plan (plan 06b: the docs check, the README, "Coordinator operations after the merge"); the design system plans (plans 03a and 03b); the design system's sidebar change on `design/recorded-tag-and-sidebar` (`Sidebar.about`). Boards on the design canvas, page "9 · About this prototype": `N-Docs-Proposal`, `N-Docs-Prediction`, `N-Docs-Proposal-Phone`, `N-Docs-Prediction-Phone` and `N-Docs-Sidebar`, all five signed by the project owner and locked (2026-10-29; he picked two pages over one).

Specific to this plan:

- **Static and offline.** The two routes make no request: no `fetch`, no React Query hook, no `EventSource`, nothing from `api/` or the owner's query hooks; they read only `readLocal('lastDesk')`, for the link into the prototype, which says "Try Desk prototype" and never names the business (project owner, 2026-10-29: no Desk data on these pages, as the spec says). A source guard and the screen tests check the rest.
- **No HTML passthrough.** The Markdown reader turns text into typed blocks and React elements only. Raw HTML in a document is an error, except the figure comments this plan defines (`<!-- figure: architecture -->`, `<!-- figure: tau3 -->`, `<!-- figure: readiness -->`). No `dangerouslySetInnerHTML` under `web/src/about/`; plan 04's guards (`RAW_HTML`, `RAW_COLOR`) already scan it.
- **Links.** A link target is `https://…`, or one of the two document file names, which become the other page's route. A link to any other repo file is refused by the parser and by a docs-side test. The repository link is known now (2026-10-31), so such links could map to it, but they stay refused by choice. One image is allowed: directly after `<!-- figure: architecture -->`, `![…](images/v1-architecture.svg)`, the committed figure GitHub readers see (project owner, 2026-10-29); the reader drops it and draws `ArchitectureFigure` instead. Any other image is refused. External links open in a new tab with `rel="noopener noreferrer"`, as `TextLink`'s `external` does.
- **The words are the documents'.** The reader shows the Markdown's text in full, in order and unchanged, with only these named changes, each tested:

It must match exactly once, with placeholders and with links filled;

### Task 2: The Markdown reader and the document registry

**Files:**
- Create: `web/src/about/links.ts`, `web/src/about/markdown.ts`, `web/src/about/documents.ts`, `web/src/about/markdown.test.ts`, `web/src/about/documents.test.ts`, `web/src/about/guards.test.ts`

- Produces:
  - `type Inline = { kind: 'text', text } | { kind: 'strong', children } | { kind: 'code', text } | { kind: 'link', href, children, internal: boolean } | { kind: 'placeholder', text }`.
  - `type Block = { kind: 'heading', depth: 1 | 2, text, id } | { kind: 'byline', text } | { kind: 'paragraph', children: Inline[] } | { kind: 'list', items: Inline[][] } | { kind: 'table', head: Inline[][], rows: Inline[][][] } | { kind: 'figure', name: 'architecture' | 'tau3' | 'readiness' }`.
