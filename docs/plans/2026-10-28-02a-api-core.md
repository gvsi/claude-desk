# Claude Desk Prototype — Plan 02a: API core

> **For agentic workers:** Execute with the repo's `executing-implementation-plans` skill (`.agents/skills/`): a fresh implementer and a task review per task, in the plan's worktree, landing through one PR after the review panel ("Before you start"). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The core of the API process (`backend/desk/api/`, port 8700) and the API half of the Friday thin slice: the typed kernel client and its contract-checked fake, append-only transcripts, check-then-reveal delivery over SSE, Claude's tool-use loop with fencing and recovery, the public chat API and the Agent Card route, approvals and resume jobs, the owner reads Plan 04's first run needs, and the evals API target. It holds only the Anthropic API key and its database role, passes the kernel session IDs and the tokens it was handed, never identities, and owns the API's HTTP contract and read models ("Shared seams"). Plan 02b builds the rest of the API on it.

**Architecture:** One FastAPI app; this plan builds its `public` and `owner` routers (Plan 02b adds setup and proving under `owner`, `agents` for A2A and `proxy`). Every kernel call goes through one typed client (`kernel_client.py`, keyed by `KERNEL_ROUTES`); tests point it at `FakeKernel`, an in-process ASGI app, and the contract suite runs against both. A request that reads `app.*` or `kernel_ro.*` first calls `GET /whoami` and takes the copy, session and generation only from the answer. Claude runs in our own loop (`loop.py`): each response is stored before any of its tool calls runs, every proposed call goes to `/decide` then `/execute`, and replies go `send_reply` → `/check_reply` → `deliver()`, the only writer of visitor-visible events.

**Tech Stack:** Python 3.13 (uv), FastAPI, Pydantic v2, httpx, sse-starlette, the `anthropic` Python SDK, Procrastinate with psycopg, SQLAlchemy 2 Core, pytest-asyncio, `cryptography` (added here for Plan 02b's built-in agent); pinned in the lock files. References: [tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview), [mid-conversation tool changes](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages), [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [Procrastinate: retry stalled jobs](https://procrastinate.readthedocs.io/en/stable/howto/production/retry_stalled_jobs.html).

**Spec / master plan:** `docs/specs/2026-10-28-claude-desk-design.md` and `docs/plans/2026-10-28-00-master-plan.md` (sections cited by name); Plan 02b is `docs/plans/2026-10-28-02b-api-owner-setup-agents.md`. Designs: canvas boards N-Public-*, N-Conv-*, N-Today-*.

Specific to this plan:

- **Process boundary.** `desk.api` never imports `desk.kernel_service`, `desk_kernel`, `desk.mockpay` or `tests`; it shares `desk.contracts`, `desk.events`, `desk.kernel_api` and `desk.presets` with the kernel. Per-request kernel client views (session, owner, agent, public) never carry another's credential.
- **Credentials at rest.** Tokens, agent private keys, codes (A2A `verify_code` too) and Demo inbox bodies live only in cookies and in the memory of the request, turn or built-in agent holding them; never in `app.*`, `procrastinate.*`, job arguments, exceptions or logs. Link tokens appear only in delivered cards' `href`.
- **Cookies carry only tokens** (`HttpOnly; Secure; SameSite=Strict`, unsigned: the kernel checks the token): `desk_owner` holds the owner token (`Path=/api/owner`, `Max-Age=604800`); `desk_visitor` holds the session token (`Path=/api/public/desks/{slug}`, `Max-Age=86400`, renewed per request: the 24 h idle close).
- **Route scopes.** Owner and setup routes under `/api/owner/` (proving under `/api/owner/policy/`), visitor routes under `/api/public/desks/{slug}/`, the kernel's public Desk at `/api/public/{slug}` (no cookie), `/api/d/{token}`, `/api/pay/{token}`, `/api/a2a/{slug}`, `/api/health`. Only creating a copy needs the passcode.
- **Visitor-visible events.** Only `deliver()` builds the four signed events; `emit()` takes the other seven (`owner_typing` among them, a master amendment of 2026-10-29); every turn ends with `EvTurnEnd`. `EvError.code` ∈ `kernel_unavailable`, `session`, `rate_limited`, `internal`, shown as static copy.
- **Errors.** `ApiError{error, code, retry_after}`. Owner and visitor routes: `KernelFailed` → its status, `{error: "kernel", code}`; `KernelUnavailable` → 503 `{error: "kernel", code}` (`seed_unproved`, `internal`, else `kernel_unavailable`); `ModelUnavailable` on a structured route → 503 `{error: "model_unavailable"}`, nothing stored. Never a silent drop. A2A bodies are `{code, disclosure: "ai"}` (Plan 02b's Task 4).
- **Model calls** as "Model cost and latency budget", with `max_retries=2`, one `app.model_calls` row each, written right after the call, `created_at` its finish (an error: `stop_reason: "error"`, zero tokens); conversation per Task 4's snippet; structured routes (`output_config.format` from a Pydantic model) on `claude-opus-5-5`: setup turns (low), card drafting, situations, rules by chat (medium), the visiting agent (low, at most 6 calls a run); triage and translations at low effort. Production refuses `ANTHROPIC_BASE_URL`.
- **Daily model budget** (production): once today's (UTC) spend on the API's own model calls (`app.model_calls`, at the master's prices) reaches `DAILY_MODEL_BUDGET_CENTS = 8000`, $80 (the owner may change it), turns hand off with no model call and other model routes answer 503 `{error: "demo_budget"}`. The kernel's reviewer and soft-promise checks aren't in that table and sit outside the $80 (master "Model cost and latency budget").
- **Prompts and templates.** Every fixed string a model sees (system prompts, output models, `SEND_REPLY_TOOL`, `REWRITE_INSTRUCTION`, `NOTES`, `DEMO_TASKS`) lives in `backend/desk/api/prompts.py`, the setup card templates in `setup_templates.py`; both are gated evals inputs (Plan 05b's `GATED_PATHS`, asked to add `setup_templates.py`).
- **Untrusted text** (messages, whispers, knowledge, website and memory reads, Desk replies the built-in agent sees, tool results) reaches a model only inside Task 2's wrappers (`&`, `<`, `>` escaped), never as system text.
- **Rate limits** (in memory per process, sliding window; 429 `{"error": "rate_limited", "retry_after": s}`, and a `rate_limit` ledger event for a window's first hit when a credential is present): per IP, `passcode` 30 failures/10 min, `copies` 30/h (a backstop against a leaked passcode in a loop; copies spend no model tokens), `new_chat` 180/h (a new visitor session; loading or resuming a chat is never limited, since a resume reuses its cookie and creates nothing), `visitor_turn` 90/h (a visitor message that starts a model turn: mode `ai`, not when the owner has the chat or it is paused), `proxy` 60/10 min, `a2a_ip` 120/h; per session, `visitor_turn` 30 per conversation, `visitor_post` 120/10 min (every message in any mode, checked before anything is stored; a backstop no real visitor reaches, since a paused chat's message still runs a reply check and a ledger entry), `verify` 10/10 min (owner decision, 2026-10-29: the money guard is on model turns and the $80 daily budget, not on page loads), `translate` 60/h (Plan 02b: the owner translations a conversation sets off, each a Haiku call, about two a turn; past the limit the owner reads the message as sent); per copy, `demo_agent` 5/h, `setup_turn` 80/h, `owner_ai` 40/h, `drafts` 40/h and `new_desk` 10/h (Plan 02b: rules drafted and confirmed, and Desks made); per agent key, `a2a` 30/5 min, counted once the kernel accepted the signature; open streams, 3 per session (a fourth closes the session's oldest, so a reload never answers 429) and 30 per IP.
- **Client IP and public origin** (Plan 06b's seam; no other header is trusted): with `TRUSTED_PROXY_HOPS = n > 0`, the n-th entry from the right of `X-Forwarded-For` (Plan 06b: 2), fewer entries or an invalid address → one shared bucket; with 0, the socket peer. A loopback peer without `X-Forwarded-For` (the built-in agent) is exempt from IP limits everywhere, and outside production every loopback peer is, so tier 2 runs locally. Public URLs use `PUBLIC_ORIGIN`.
- **Connections and state.** One `LISTEN desk_run_events` connection per process fans wake-ups out by `session_id`; pools: API 20 (+10, `pool_timeout` 5 s), turn locks 10, Procrastinate 5; a pool timeout in a turn → `EvError{code: "internal"}`. Plan 06b runs one task; in a deploy's overlap, in-memory state (agent runs, running proofs) is on one task, so a run poll may 404 and a proving retry restarts.
- **Owner-facing copy the API composes** (labels, safety rows, suggestions, questions): sentence case, plain, no "→" or exclamation marks.

## What this plan serves

- The public Claude: a stranger sees "Claude is writing", then a reply checked before it appeared, each action's result attached under it as a signed receipt.
- Acting for the owner without being talked around: Claude only proposes, the kernel decides, a held request returns at once ("I've asked Maria"), and the owner's answer resumes the chat with the visitor's own credential.
- The owner in the loop from day one: four answers on a held request, and Today, what needs them, each conversation, the Answering switch and a ledger that verifies.
- On the hosted Desk, the Friday thin slice end to end: quote, hold, approve, execute, a checked receipt and a verified ledger.

**Transcript contract** (`store.py`; the master's loop contract, append-only):
- A model context is the session's rows with `model_seq` in the current `model_context`, in order, opening with a `context_start` row: its frozen `tools` (`tools_declared`, with `defer_loading: true` on those not in `tools`, then `send_reply`), its frozen system prompt (sent unchanged on every call in the context, since replayed thinking is bound to it; a turn whose rendered prompt differs, after a deploy or a rename of the business, Desk or owner, starts a fresh context, as does a model 400 saying a thinking block is bound to another conversation, once per turn while a call is left; a changed prompt waits for at most the one recovery turn, the turn a request runs so Claude reads the results of calls a stopped turn left open, which runs on the stored prompt so Claude reads them in the context that made the calls, and any other turn opens the new prompt at once, its summary carrying the results Claude hadn't read) and, after the first context, the code-built summary. Rejected: delivering a changed prompt as an appended `role: "system"` message (it keeps old chats on a stale base prompt) and `drop_block` (it silently loses reasoning and costs output tokens). Assistant rows replay `model_content` unchanged, thinking included; rows between merge into one user message, `tool_result` blocks first.
- Before each call, pending model-visible rows get the next `model_seq` and a frozen block: `visitor_text` `<visitor_message>`, `agent_text` `<agent_message>`, `owner_say` `<owner_said_to_visitor>`, `whisper` `<owner_whisper>` (an untrusted owner note in the user turn), `action_update` `<action_update decision_id state result_fact_ids?>{visitor_plain}` (the optional `result_fact_ids` attribute is a space-separated list of IDs, escaped by the wrapper; its state and IDs also live in the row's `blocks` metadata so the summary retains the decision/state/result-ID association without parsing the frozen text), `delivered` not by Claude `<shown_to_visitor>`, `desk_context` `<desk_context>{facts, knowledge}`, `note` `<note>` (`NOTES`), and the summary `<conversation_so_far>` (texts, delivered blocks, says, action updates, the latest verification note and the latest take-over, hand-back or resume note, and the results of Claude's last calls it hadn't read, one line each, escaped and labelled by author, kind or tool, built by code; whispers never). User-turn rows come first; all pending `tool_change` rows then form one `role: "system"` message of `tool_addition` / `tool_removal` blocks (`{"type": …, "tool": {"type": "tool_reference", "name": …}}`), always last before the assistant turn, never `messages[0]`. Claude's own `delivered` rows aren't replayed (its `send_reply` call is); `status` and triage rows never are.
- Each assistant response is written (frozen) before any block is routed; the results row (each `tool_use` answered once, in block order) follows. Until then `prepare_model_input` raises `UnansweredToolUse` and `run_pending` recovers by call ID (Task 6), so an action that ran is never re-proposed under a new ID. Pending work: `model_seq` null and `wake` true (visitor and agent text unless the owner has the chat, whispers, action updates, the verification note); a `desk_context` row only when `/context`'s facts and knowledge change.
- Tool-set changes (`tool_delta`, Task 4), mode `"append"`: a declared tool now in `tools` → `tool_addition`; one leaving `tools` → `tool_removal` (the entry stays); a changed definition → `tool_removal`, then a fresh context with the new entry (an entry is never edited, which would break replayed thinking); an undeclared tool, or any change in mode `"fresh_context"` → `start_fresh_context`. Nothing earlier is edited or deleted; a regenerate with feedback appends.
