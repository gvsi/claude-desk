## Global Constraints

The master plan's "Global Constraints" apply as written, and so do Plan 01a's plan-specific constraints (shipped reports regenerate with `make proofs` into `kernel/cedar/proofs/`). Specific to this plan:

- **Builds on Plan 01a.** Starts from Plan 01a's Task 16 commit (every task needs its execute, approvals, `/context` or reply check), rebases onto 01a as merged, and changes 01a's files only where a task names them, never weakening a check, test or fixture.
- **Kernel only.** API proxies are Plan 02, screens Plan 04, CI Plan 06a.
- **One test at a time.** Step 1's tests are written, run failing, implemented and passed one by one in order; Step 2's FAIL is the first one's.
- **Codes stay in the kernel.** A verification code exists only as a hash in `verification_challenges` and as text in a `demo_inbox` body; never in a ledger summary, a `kernel_ro` view, an `InboxNotice`, `VerifyStarted`, `model_view`, a log line or anything Claude sees.
- **Link tokens.** Document-link tokens are `secrets.token_urlsafe(32)`, live 24 hours (`LINK_TTL`), and are stored only in `kernel.document_links`, beside their sha256 (`token_sha256`), which is all the copy resolver reads: never in a `kernel_ro` view, a fact claim, `model_view`, a ledger summary or a log line (access log included). Facts name the link by `link_id`; the reply check looks the token up (`href_for`), and visitors see it only in a signed card's `href`.
- **Ledger summaries** pass Plan 01a's `check_summary` (no `canary`, `contact`, `text` or `token` key, no email-like value); refs written to `desk_data` match `^[A-Za-z0-9_-]{1,64}$`, else 422 `invalid`.
- **Errors.** Non-2xx answers carry the master's `KernelError` codes; a failure that resolves no Desk goes to the structured log, not the ledger.
- **Lock order** (Plan 01a's, in `repo.py`, extended; Task 3g). Plan 01a orders the session row, the decision row, the execution row, the Desk's active `policy_versions` row, a payment link, an adapter's own rows and, last, the ledger head; nothing takes a row lock after it holds the ledger head. This plan's rows fall in it as sessions, then links, then documents and facts, then the ledger head:
  - **Verification challenges** come after the session row and the people they belong to. `/verify/start` and `/verify/check` lock the session row `FOR UPDATE`, then the people (in ID order), then the live challenges, then (on a right code) the session's facts `relabel_on_verify` moves, then the ledger head. A verification start's T2 takes the people and challenges as its adapter's own rows, after the decision and the execution row. `DELETE /desks` cancels live codes after it closes the sessions.
  - **Document links** come after sessions and before documents and facts. An open takes its link (one `UPDATE`), then the link's fact, then the ledger head. Voiding (removing a person, changing a person's contact, deleting a Desk) takes the sessions, then the links, then (removing a person) the person's documents, then the links' and documents' facts, then the ledger head. A release inserts its link and fact under fresh keys in T2, which wait for nothing.
  - **Knowledge rows** fall with documents and facts: `POST /knowledge` writes its row (an upsert, which locks an item it replaces), then its `desk_data` entry.
  - The owner's Desk-data routes hold the Desk row first (`owner_desk`). `PUT /desks/{id}/people` then takes the open sessions verified as the people it removes or gives another contact, then the Desk's people and their live challenges, in verification's order. A session a check verifies as one of them after that session step and before the write holds their row is taken once the people are held and closed with the rest; that late lock waits on nothing that waits on the write (`repo.py`). `POST /handoffs/{id}/done` also holds the Desk row first, then the handoff, its fact and the ledger head.
  - **The receipt-ready refusal** (`execute._receipt_ready`: a tool with no executed line, 500 `internal`) writes its `execute` entry in a fresh transaction without locking the decision the entry names (a refusal that changes its decision, such as `_stale`'s, locks it first). It takes no other lock, only the ledger head, so it never holds the head while it waits for a row.
- **Migrations** (master "Shared seams"). Revisions `01b_1_verification`, `01b_2_handoffs`, `01b_3_people`, `01b_3b_money_cap`, `01b_5_knowledge`, `01b_6_document_links`, `01b_5b_knowledge_view`, `01b_3e_money_cap_edges`, `01b_1b_inbox_challenge` add to master Task 2's tables (`ADD COLUMN IF NOT EXISTS`, `CREATE [UNIQUE] INDEX IF NOT EXISTS`) in a chain whose first `down_revision` is `main`'s head at merge: one head.
- **The PR touches `web/` with generated types and one mock check only.** Task 3b regenerates `web/src/api/contracts.gen.ts` (and `web/src/api/openapi.gen.ts` when `npm run gen:api` moves it), and the mock's list of fields typed ahead of the contracts (`web/src/mocks/validate.ts`) drops `auto_money_cap_cents` now that the contracts carry it; neither changes rendered output. The mock API's seed data already sends the active rules version's `auto_money_cap_cents` on `main`. Under AGENTS.md's rule that edits under `web/` changing no rendered output aren't design PRs, the PR merges on the review panel and CI; its description says that nothing visible changes.
- **Evals gate.** Each task's Step 4 also runs `make evals-tier1` (every `01a` row green); `01b` rows stay `pending 01b` until Task 7 lands them, so a task's own tests are its evidence. Tier 2 per Task 7.

## What this plan serves

- Who's asking decides what Claude can touch: a person who proves who they are with a code sent to the contact on record gets their own records, and nobody can redirect that code or tell from Claude's reply whether a contact exists.
- The owner shapes the Desk: business details, hours, prices, people, documents and knowledge go through the kernel into the ledger, and Maria can speak in the chat or whisper to Claude.
- Private data leaves only to its owner: a verified customer gets their own invoice by a single-use link, and a document's hidden marker is caught in a reply, a tool result or knowledge, even split by spaces, case or character width, and the reply goes to Maria instead.
- A first-time visitor sees the verify card, their code in the Demo inbox, a lead or callback saved for Maria with the contact they gave, and a document link that opens once.
