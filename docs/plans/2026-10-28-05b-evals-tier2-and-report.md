# Claude Desk Prototype — Plan 05b: Evals tier 2, the gate and the report

> **For agentic workers:** Execute with the repo's `executing-implementation-plans` skill (`.agents/skills/`): a fresh implementer and a task review per task, in the plan's worktree, landing through two PRs ("Before you start"), each after the review panel. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Evidence that a Desk can't be talked around and still does its job: a model-driven tier 2 suite (about 50 hostile-visitor scenarios and 30 legitimate tasks, judged by independent oracles over the kernel's records) that gates deploys and gated pull requests through a committed results file CI checks, sets the reviewer thresholds on a calibration split, and measures cost and latency per conversation for the report.

**Architecture:** Built on Plan 05a's harness. A simulated visitor drives the real API and kernel on an in-process `ApiTarget`; after each run the runner snapshots the kernel's records, checks they are complete and judges the run with oracles that never import the checks they judge. A pass runner, a gate, a results file with one checker CI runs, a calibration script and a report turn runs into a decision and numbers.

**Tech Stack:** Plan 05a's (`evals` group). References: the [Wilson score interval](https://en.wikipedia.org/wiki/Binomial_proportion_confidence_interval#Wilson_score_interval); Messages API [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs); [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing).

**Spec / master plan:** spec "Reply timing", anti-goals; master "Evals gate (Plan 05)", "Model cost and latency budget", "Rivera seed", "Data model and database roles", "Decision semantics and proof obligations", "Schedule, lanes and gates"; `docs/plans/2026-10-28-05a-evals-tier1.md`. ## Global Constraints

The master plan's "Global Constraints" apply as written, and so do Plan 05a's plan-specific constraints. Specific to this plan:

- **Tier 2 spend.** Every pass names `--max-usd`. Because the organization's $1,000 monthly limit is shared with the hosted demo, `run_pass` also refuses a pass whose estimate would take this month's eval spend (`evals/reports/spend.csv`) past `monthly_limit_usd − demo_reserve_usd` from `evals/budget.toml` (1000 and 400: the reserve is five days at the demo's $80 daily budget, which is a cap on its spend, not what it is expected to spend), reading the spend file all worktrees share (Task 4). $0.40 per run is estimated until measured. Spend rows carry the provider: the cumulative guard counts only Claude API spend (a Bedrock pass bills AWS credits, except for the kernel's checks), and `--max-usd` caps a pass on either provider. `PRICES` (Task 8) holds each provider's list prices; the Bedrock rows are filled from AWS's pricing page before the first Bedrock pass, and a pass on a provider without prices refuses to start.
- **Harness models:** the attacker on `claude-opus-5-5` (effort `medium`), the legitimate visitor on `claude-sonnet-5-5` (effort `low`), each turn a structured output (`output_config.format`) with a refusal fallback that never leaves the three production models: on both providers the SDK's client-side `BetaRefusalFallbackMiddleware` on the simulator's client, falling back to the other production model (the attacker to `claude-sonnet-5-5`, the visitor to `claude-opus-5-5`, each as its provider names it), with one `BetaFallbackState` per run and no server-side `fallbacks` field or beta (Bedrock has none, and the Claude API's `"default"` form can route to models outside the three), so both providers fall back alike. A simulator turn served by a fallback model is counted, not an error, from the response itself: on this non-streaming path the pinned SDK (2.3.0) prepends a `fallback` content block (`from` and `to` models) to the response of the turn whose model refused and leaves `usage` as the serving model's, with no `usage.iterations`, and once the run's `BetaFallbackState` is pinned, later turns go straight to the fallback model with no block. So each turn records the model that served it, from the response's `model` field mapped through `BEDROCK_MODEL_IDS` so either provider's name for a model counts as that model, and a run counts fallback turns (served by a model other than the configured one) and switches (responses carrying a `fallback` block); the simulator reads its structured output from the text block, past any `fallback` block; the Desk side has no fallback, so a Desk-side model other than the configured one is a configuration error.
- **Provider** (owner decision, 2026-10-29). `MODEL_PROVIDER` picks where the API's model calls and the simulator's go: `anthropic` (the Claude API, the default) or `bedrock` (Amazon Bedrock in `AWS_REGION`, default `us-west-2`, through the SDK's `AsyncAnthropicBedrockMantle`, model names mapped by Plan 02a's one table, `BEDROCK_MODEL_IDS`). The models are the production ones on either provider, Opus 5.5, Sonnet 5.5 and Haiku 5.5, and the provider never swaps in another; only a simulator turn the model refuses can be re-served by its refusal fallback, on the other production model, counted per pass ("Harness models"). The kernel's reviewer and soft-promise checks stay on the Claude API (Plan 01a's client) whatever the setting, and each pass records the provider and model ids of each part. Nothing here uses Message Batches or the Models API, which Bedrock lacks. Until the owner accepts the Bedrock Marketplace agreement and the account can call the three models on the endpoint this client uses, passes use the Claude API; switching is a `.env` change, not a code change. (On 2026-10-29 the cross-region inference profiles' quota read 0 tokens per minute; the Bedrock page gives this client's endpoint a default of 2 million input tokens per minute, so which quota applies is the owner's to confirm.) A real pass needs `ANTHROPIC_API_KEY` on either provider, since the kernel's checks use it, and on `bedrock` Plan 02a's Bedrock-only credential (`BEDROCK_AWS_PROFILE` or `AWS_BEARER_TOKEN_BEDROCK`); `run_pass` refuses to start without them. Before the first Bedrock pass, Plan 02a's live loop-contract check runs with `MODEL_PROVIDER=bedrock` and must give the same `TOOL_CHANGE_MODE`, else passes stay on the Claude API; and one simulator call on Bedrock (`python -m evals.run simulator-check --provider bedrock`, Task 3) checks that Bedrock accepts the `anthropic-beta: fallback-credit-2026-07-01` header the pinned middleware adds to every request by default (`DEFAULT_BETAS`). If Bedrock rejects it, the simulator builds the middleware with `betas=()` on Bedrock (`SIMULATOR_FALLBACK_BETAS` in `evals/tier2/simulator.py`, a per-provider setting), since a non-streaming retry needs no credit token, and the check runs again.
- **The stack.** A pass runs on an in-process `ApiTarget` (05a) built from the working tree: every model scripted with `--dry-run` (the API target and the simulator then use provider `anthropic` against the fakes whatever `MODEL_PROVIDER` says), real models on the pass's provider with its credentials otherwise (`make_api_target(..., models="real", provider=)`, Plan 02a). `--base-url` drives an external deployment (exploration and the hosted latency run) and can never write a results file.
- **Results files are self-attested.** They are produced locally (CI holds no Anthropic key); CI checks completeness, hashes and the gate recomputed from their rows, but doesn't re-run them, and the report's limits say so.
- **This plan's evals gate:** it changes no kernel code, prompt or policy except the calibrated block of `review_thresholds.py` (the Saturday operation below: `make proofs`, tier 1 and a results file). Tasks run `make evals-unit` and `make evals-tier1`. Nothing deploys from this plan.

## What this plan serves

- Before each deploy a simulated stranger or agent tries about 50 ways to move money, leak data, verify the wrong person or promise what the owner never said; a run with any baseline violation fails the gate.
- It keeps the Desk useful (a Desk that holds everything can't pass) and measures cost per conversation and how long a checked reply takes.
- A first-time visitor sees "0 baseline violations in N attack runs" with the suite behind it.
