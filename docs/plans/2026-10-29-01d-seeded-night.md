# Claude Desk Prototype — Plan 01d: Seeded night (a recorded week, replayed into each copy)

> **For agentic workers:** Execute with the repo's `executing-implementation-plans` skill (`.agents/skills/`): a fresh implementer and a task review per task, in this plan's worktree, landing through the two PRs in "Landing" after the review panel. Steps use checkbox (`- [ ]`) syntax for tracking. This plan builds on the three kernel plans (01a, 01b and 01c) as merged.

**Goal:** A visitor's demo copy opens on a business that has already been working: a week of conversations (most of them last night) that ran once through the real API, kernel and Desk models, recorded, and replayed into each new copy at creation as data, with times moved to the visitor's week and every ledger entry marked and signed as replayed. Today's "Since last night" and "Last 7 days", Conversations, People, Safety and the ledger read that history, each labelled as recorded. Nothing runs on a schedule, and nothing replayed can be acted on.

**Architecture:** Three parts. A recording script drives seven scripted personas (fixed text) against the API core's in-process API target (plan 02a) with the real Desk models, then a closing step settles the copy and exports the night into a strict, scrubbed recording file that holds references, never amounts or appointment times. The kernel loads that file at startup and replays it inside `POST /copies` when the API asks (`replay_night: true`): it re-derives every price and slot from the new copy's own seed, writes the records with fresh ids and moved times, appends their ledger entries with a signed `summary.replayed` marker that only replay can write, re-renders and re-signs the replies, and returns them in `CopyCreated.replayed_messages` for the API to store. A recording that is missing, stale or can't be replayed in full gives a copy with live data only, logged, and so does the kernel's off switch, `REPLAY_NIGHT_OFF=1`.

**Tech Stack:** the kernel plans' stack (01a–01c) and stdlib `zoneinfo`; the recorder uses the API core's `make_api_target` (plan 02a) and the tier 1 evals' kernel target and fake model server (plan 05a). The recorder and every backend test that imports the evals (the shared fixture, the ledger oracle, the fake model server) run from the repo root in the tier 1 harness's own environment, `PYTHONPATH=. uv run --project backend --group evals`: the repo root on the path for `evals`, the evals dependency group, and the backend's pytest settings adding `backend/`. No new dependencies.

**Spec / master plan:** `docs/specs/2026-10-28-claude-desk-design.md` ("Owner experience": Today's "Since last night" and "Last 7 days"; "First visit and hosting"; "Safety and enforcement architecture (locked)"); `docs/plans/2026-10-28-00-master-plan.md` ("Turner seed", "Shared contracts v2" (`LedgerEvent`, `CopyCreated`), "Kernel HTTP API v2", "Reply check and visitor-visible text" (Clauses, Labels), "Data model and database roles", "Evals gate"); the API core's Task 9 ("Today's windows", plan 02a); the API owner plan's Task 13 (storing the replayed night, plan 02b); the web app's Tasks 5–6 (the labels, plan 04); the tier 1 evals (harness, kernel target, ledger oracle; plan 05a); the tier 2 evals' Task 4 (`GATED_PATHS`, `inputs_key`; plan 05b).

## Global Constraints

The master plan's "Global Constraints" and the kernel core's plan-specific constraints (plan 01a) apply. Specific to this plan, seven safety rules, then freshness and the evals gate:

1. **Replay is data, never decisions.** Replay calls no adapter method (`normalize`, `execute`, `reconcile`), no `/decide`, `/execute`, `/check_reply` or approval route or the functions behind them (`decide.decide_call`; `execute.execute_allowed`, `run_approved`, `recheck`, `prepare_intent` and the reconcilers; `approvals.answer`; `reply_check.check_draft`, `check_clauses` and `finalize`), no model (the reviewer, the soft-promise check) and no outbound HTTP. It uses only the pure helpers rule 5 names: `quote.price` and `quote.discounted`, `render.render_clause` and `render.status`, `reply_check.scan_prose` and `sign_verdict`, `decide.sign_decision` and the functions `decide` writes its texts with, `desks.next_open_window` and `desks.mask_contact` (`test_replay_calls_no_adapter_decision_execution_check_or_model`). It writes only what the recording file shipped in the image says, re-derived against the copy's seed (rule 5), from inside `POST /copies`. No route accepts or returns recording data: the export runs in the recorder's process through kernel code, so the API can't inject history (safety invariant 5).
2. **Terminal states only.**
   - Decisions are only `executed`, `refused`, `denied` or `expired`.
   - Never replayed, in any state: approvals, verification challenges, document links, payment links, mandates and their reservations, agent keys and nonces, Demo inbox entries; nor charges, refunds or `executions` rows.
   - Quotes replay `expired`, and so do their `quote` facts and `slots` facts. Callbacks replay as handled: handoffs `done` (owner decision). `booking` and `handoff` facts are `committed`. No replayed fact is `available` or `proposed`, and there is no `consumed` status.
   - Sessions replay closed.
   - The recorder's closing step (Task 3) settles what has a terminal form and refuses the export if anything else is still live, naming it; it never drops a live record silently.
   - The seeded held request (the kernel core's Task 12, plan 01a) stays live and real, outside the recording.
3. **No person in replay.** Replayed sessions carry no person: `person_id` null, `verified` false, assurance `none` (never `demo_code`). No replayed fact, booking or ledger summary names a person, and replayed facts are labelled `["owner", "session:<replayed id>"]` only, never `person:`. A recorded message may still say that a customer confirmed who they were; that is text, not state. No persona releases a document, so no link fact exists, and Dana's persona, asking for her invoice without verifying, gets no document. The private-data baseline never reaches recorded material: a visitor who verifies as the copy's Dana can read or cite none of it.
4. **Honest time, and a marker only replay can write.** A ledger entry's signed `created_at` is the real append time. The moved time a replayed event shows is `summary.replayed = {"at": <SignedTime>, "recording": <recording_id>}`, inside the hash and signature, so it can't be stripped and the chain verifies end to end (no new `LedgerEvent` field, which would change every entry's hash). Only kernel replay writes it:
   - `ledger.append` takes the marker as an explicit parameter, `replayed: ReplayedMark | None = None` (`ReplayedMark{at: SignedTime, recording: str}`, kernel-internal). It runs `check_summary` on the caller's summary first, which refuses the key, then hands the marker to the private `_append_one(..., replayed=)`, which adds the key after its own `check_summary`, so replay's own entries pass; `_checkpoint` passes none;
   - a summary that already carries `replayed` is refused, by `POST /ledger/append` (422 `invalid`, nothing appended) and by every kernel append (`ledger.check_summary` raises `UnsafeSummary`), so no API-reported or other kernel path can mark an entry;
   - only `seed_night.replay` passes the parameter.
   Replayed entries are kernel entries only: the night's API-reported entries are not replayed, so no reported entry comes back as checked. Replayed kernel rows carry `replay_id` (the recording id) and moved times ("Times" below); only ledger entries keep the real append time.
5. **Visitor-visible text stays kernel-made: re-derived, all or nothing.** The recording holds no money amount and no appointment or callback time: only item ids and quantities, discounts in basis points, and slots as `{weekday, start_local}`. Replay computes every price and amount from the copy's own price list (the quote adapter's `price` and `discounted`), every slot from the slot map below, every callback window from the copy's hours, and every public seed fact a card cites from the copy's own seed by its key ("Seed facts" below), so claims are written by kernel code as master "Clauses" requires. If any replayed price, amount, slot or seed fact can't be re-derived from the copy's seed, the whole replay is refused and the copy gets live data only, logged (owner decision); there is no partial history. Cards are rendered by `render.render_clause` from the replayed facts; prose passes `reply_check.scan_prose` again; decision texts are rebuilt by the kernel functions `decide` writes them with; every verdict and decision is re-signed for the copy's ids. A recording that fails any of this fails the validator, and CI.
6. **Scrubbed.** The validator refuses a recording holding a verification code, any token, a document canary or body, model usage, any field outside its strict models, or any contact except the callback persona's. `personas.py` fixes that one as a reserved example, `(510) 555-0163` (`+15105550163` normalized), a number no seed record uses (not Turner's own `(510) 555-0142`, and not the `(510) 555-0177` the kernel's tests use), and the validator matches it exactly; every other contact, the business's and the seed's people's included, is refused. Replay writes it into owner-visible rows masked by `desks.mask_contact`, as owner views show any contact.
7. **Opt-in, with an off-only switch in the kernel.**
   - `CreateCopyRequest.replay_night: bool = False`: the kernel replays only when asked.
   - The API's `Settings.replay_night` is a code constant, never read from the environment (the API owner plan, plan 02b): on for the hosted demo's copy routes, False in `make_api_target` and in the recorder's target, so tier 1, tier 2 and the recording's own copy never replay.
   - The kill switch is the kernel's, since replay runs in the kernel at copy creation: the kernel reads `REPLAY_NIGHT_OFF=1` from its own environment at startup and, when it is set, ignores `replay_night: true` and gives every copy live data only, logged once as `seed_night_unavailable` (switched off). It can only turn replay off, never on, so no environment makes an eval or recording copy replay; using it takes a task restart, not a new image. The API reads no replay flag from its environment, as the API owner plan (plan 02b) also says.
   - A missing, stale or failing recording gives live data only, logged, never a 500 (owner decision): `seed_night_unavailable` once at startup with the reason, or `seed_night_refused` or `seed_night_failed` for the copy.
- **Freshness.** The recording names the code it ran under in two keys, plus the seed:
  - `inputs_key`: the tier 2 evals' `inputs_key` algorithm (plan 05b) (the first 16 hex of the sha256 of `canonical({path: git rev-parse <rev>:<path> or null})`) over `KERNEL_INPUT_PATHS`, the kernel and policy part of its `GATED_PATHS`: `kernel`, `backend/desk/kernel_service` (seed and review thresholds included), `backend/desk/api/prompts.py`, `backend/desk/api/setup_templates.py`, `backend/desk/presets.py`, `backend/desk/money_cap.py`, `backend/desk/contracts.py`, `backend/desk/kernel_api.py`, `backend/desk/mockpay`. It needs git, so it is checked on the host.
  - `image_inputs_sha256`: the sha256 over each file's path and content sha256 under the same paths as the app image ships them (`kernel` narrowed to `kernel/cedar`; `__pycache__`, `*.pyc` and dotfiles skipped), computed the same from a checkout or inside the image, so the kernel checks it at startup and `make image-check` runs that same check inside the built image (Task 2).
  - `seed_sha256`: the Turner seed as JSON with ids, canaries and dates normalized.
  The recorder refuses uncommitted or untracked files under those paths and stores `git_sha`. The file and the rest of `backend/desk/seed_night/` (format, validator, personas) sit outside both keys and outside `GATED_PATHS`, so recording doesn't make the file stale; that code runs only for copies that ask for replay, which eval copies never do, and its tests and Task 5's tier 1 cases guard it. Any later change under the key, replay's own code included, means re-recording: about 15 minutes and about $3.
- **Evals gate** (master "Evals gate"). Replay is kernel code: `make evals-tier1` on every task; this plan's cases are `requires("01d")` (Task 5), and its PR 1 commits a tier 2 results file at its rebased head.

## What this plan serves

- A first visit shows the idea at work: the visitor's Today opens on a real night (bookings, a lead, a callback handled, a discount held and declined, an attempt stopped) instead of zeros, and every figure comes from records the kernel wrote.
- Honesty about it: every surface that shows recorded history says so, the ledger marks each recorded entry inside its signature, and the README says how the night was made, retries included.
- The safety story holds for recorded material too: nothing replayed can be approved, executed, paid, verified against or read by a visitor, and the chain still verifies end to end.

## Replay rules

**What the recording holds, and what replay writes.** Every replayed row gets a fresh id, `replay_id` and moved times.

| Record | The recording holds (references only) | Replay writes |
|---|---|---|
| Sessions | `ref`, `persona`, `kind` (`visitor` or `agent`), `language`, `day_offset` (0–5, 0 = last night), `start_local` (`HH:MM`), each event's `offset_s` after the session's first event, `attempts` (1–3: the recorder's tries, the last one kept) | closed sessions at generation 0 with no person, `verified` false, assurance `none`; agent sessions with null `agent_key_id` and `mandate_id`; a secret hash of a token no one receives, so no request can name them |
| Turns and replies (what the API delivered) | each visitor turn's text (the persona's fixed words); each delivered reply's prose blocks, clauses as `{template, fact_ref}` (a replayed record's ref, or a seed key: "Seed facts"), `ok` and violation kinds; a draft the check blocked only as its `reply` ledger entry (violation kinds, never its text), followed by what was delivered after it (the rewritten reply or the handoff clause) | `ReplayedEvent`s: replies re-rendered from the replayed facts and re-signed at generation 0 with their replayed `reply` entry's `seq`; a blocked draft's entry replays with no event, so it counts as a stopped attempt in Today and Safety |
| Decisions and actions | tool, outcome, state, `card_ids` (present in the copy's active cards), reason code, reviewer scores, the action's resource ref, items and quantities, `discount_bp`, slot ref | rows at the copy's active policy version, amounts priced from the copy's list, slots from the slot map, texts rebuilt by `decide`'s functions, `ledger_seq` the entry that recorded the final state; re-signed |
| Quotes | the action ref, items and quantities, `discount_bp` | `expired`, priced from the copy's list, `expires_at` at the session's close; the `quote` fact's `expires` claim (the card's "Good until") is the moved creation time plus the quote adapter's 72 hours (`QUOTE_TTL`), so the card reads as the visitor saw it while the `expired` status keeps the quote unusable |
| Bookings | the action ref, slot ref | `confirmed` on the mapped slot, no person |
| Leads | display name, note | as recorded |
| Handoffs | name, `RESERVED_CONTACT`, reason | `done`; reason `<name> · <masked contact> · <reason>`; window from `next_open_window` at the replayed request time |
| Facts | kind (`quote`, `slots`, `booking`, `handoff`), the record it describes, slot options as slot refs; no seed fact ("Seed facts") | claims rebuilt from the replayed rows; `quote` and `slots` `expired`, `booking` and `handoff` `committed`; labels `["owner", "session:<replayed id>"]` |
| Ledger | kernel entries of kinds `session`, `decide`, `review`, `breaker`, `approval`, `execute`, `reply`, each with `session_ref`, `offset_s`, `ref` (`decision`, `message` or `session`) and a per-kind strict summary of refs, without model usage | one `ledger.append(..., replayed=ReplayedMark(at, recording))` per entry, in shown order (ties in recorded order), with `session_id`, `ref_id` and the summary's `session_id`, `decision_id`, `action_id`, `message_id` and `fact_ids` remapped (a seed key resolved against the copy's seed) and its `policy_version` set to the copy's active version; an `approval` entry's `ref_id` names the replayed decision |
| Never | approvals rows, verification challenges, document and payment links, mandates and reservations, agent keys and nonces, Demo inbox entries, charges, refunds, `executions`, people; the seed's own rows and entries, the seeded hold and its graph, head checkpoints, API-reported entries | nothing |

**Times.** Each session's events land at `start_local` plus their `offset_s`, on the local date `day_offset + 1` days before `now`'s local date, in the business's time zone (`zoneinfo`, `fold=0`), stored in UTC. The validator holds every session to one local date between 07:00 and 23:59, and a `day_offset` 0 session to 18:00 or later, so last night falls in Today's "Since last night" (18:00 yesterday to now, the API core's Task 9, plan 02a), `day_offset` 5 on the oldest date of "Last 7 days", nothing at or after `now`, and no recorded time in a skipped or repeated hour. Every time on a replayed row (`created_at`, `updated_at`, `expires_at`, `closed_at`, `last_seen_at`, approval and execution times) takes its event's moved time, so reads that bucket by `created_at` work unchanged; ledger entries keep the real append time, with the moved one in `summary.replayed.at`.

**Slot map.** One map from `{weekday, start_local}` to the copy's first `calendar_slots` row with that local weekday and start after `now`, used for bookings, actions (resource id and `starts_at`), `booking` and `slots` facts' claims and any slot id in a summary. Appointments aren't moved back with the conversation: in the copy, as when recorded, they are future slots. A slot ref with no copy slot, two bookings on one ref, or a mapped slot already booked refuses the whole replay.

**Seed facts.** A reply may cite the seed's public facts: the charter's `charter:hours`, `charter:contact` and `charter:policy:*` facts, which the `hours`, `contact` and `policy` cards render (the deposit policy, `charter:policy:first_visit`, among them). The recording refers to one only by that stable key, `{seed: "<key>"}`, in a clause's `fact_ref` and a summary's `fact_ids`, never with its claims, and holds no row for it. Replay resolves the key against the new copy's own seed: the card renders from the copy's fact with that key, and the summary names it; no seed fact is copied, written or marked. Price-list items are named the same way, by their `item_id`. A key the copy's seed doesn't write refuses the whole replay (rule 5).

**Ledger order and checkpoints.** Replayed entries come after the seed's own, in shown order. Replay's own head checkpoints (every 50th entry) are real, unmarked entries with their owner Demo inbox notice.
