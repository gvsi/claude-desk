> **For agentic workers:** Execute with the repo's `executing-implementation-plans` skill (`.agents/skills/`): a fresh implementer and a task review per task, in this plan's worktree, landing through the PRs in "Landing" after the review panel. This plan builds on Plans 01a and 01b as merged; only Task 1, which reads no money cap, may start from the kernel verification and owner data plan's Task 6 commit (plan 01b; master "Schedule, lanes and gates").

**Goal:** The kernel's money, agent and setup surfaces: mock payments over MCP with pinned, drift-checked tools; single-use payment links with a signed `payment_confirmed`; charges and refunds through trusted adapters; signed visiting agents (`AgentAuth`, the kernel side of A2A, Agent Card blocks), demo agents and mandates with reserve, commit and release; the setup tools and safety probes; the Turner seed rows marked 01c. Lands by the Friday 18:00 gate.

**Architecture:** The kernel runs the mock payments server (`backend/desk/mockpay/`, MCP streamable HTTP on 127.0.0.1:8702) as its supervised child and only client. New tools are trusted adapters on Plan 01a's "Kernel internals" seam: every call goes `/decide` → `/execute` with intent first, mandate spend is reserved in `prepare` with the intent, and MCP tools are re-listed and hash-checked in the execution re-check on both paths. Agent signatures and mandates are checked on every agent call.

**Tech Stack:** Plan 01a's stack plus `mcp==2.3.0` (v2 API: `mcp.Client`, low-level `mcp.server.lowlevel.Server`; [migration guide](https://py.sdk.modelcontextprotocol.io/v2/migration/)), `httpx2==2.13.1` (already required by `mcp`; the `sni_hostname` [extension](https://www.python-httpx.org/advanced/extensions/)), `uvicorn==0.54.0`, `cryptography==50.0.2` ([Ed25519](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/)), stdlib `ipaddress` and `html.parser`. Every new pin is at least two weeks old.

**Spec / master plan:** `docs/specs/2026-10-28-claude-desk-design.md`; `docs/plans/2026-10-28-00-master-plan.md` (cited by section); `docs/plans/2026-10-28-01a-safety-kernel-core.md`, `docs/plans/2026-10-28-01b-kernel-verification-owner-data.md`. ## Global Constraints

The master plan's "Global Constraints" apply as written, and so do Plan 01a's plan-specific constraints. Specific to this plan:

- **Plans 01a and 01b** change only where a task names them, never weakening a check, test or fixture.
- **Receipts** (owner sign-off, 2026-10-29; Plan 01b Task 6b): the task that registers each visitor or agent tool adds its executed receipt line to `render/{en,es}.py`, so Plan 01b's `test_every_visitor_tool_has_receipt_lines` stays green: Task 2 `native.payment_link` "Payment link made for this quote" / "Enlace de pago creado para esta cotización"; Task 5 `payments.list_charges` "Charges read from {owner}'s payments" / "Cargos tomados de los pagos de {owner}" and `payments.create_refund` "Refunded to the original payment" / "Reembolsado al pago original"; Task 7 `native.charge_mandate` "Charged within the limit of your mandate" / "Cobrado dentro del límite de tu mandato". Owner setup tools (Task 8) get none.
- **Deadlines** (below the API client's 6 s timeout): MCP re-list and calls `MCP_DEADLINE_S = 2.0`; provider writes `PROVIDER_DEADLINE_S = 2.0`; provider reads at normalize `READ_DEADLINE_S = 1.0` (normalize plus the 4 s reviewer stays under 6 s); website fetch `FETCH_TOTAL_TIMEOUT_S = 4.0`. An execution path stays within 5 s (re-normalize, re-list, call).
- **Execution outcomes** (01a's seam): a spend reservation is written in `prepare`. `AdapterFailure` only when the request never reached the provider, the provider refused it (4xx, MCP `isError`), or the tool only reads; any other exception after the intent row is `unknown`. Reconciliation never trusts a lookup miss: it settles the key at the provider (`void`, or `cancel` for a checkout), so a delayed request fails instead of landing after a release.
- **Payment-link tokens** follow Plan 01b's link-token rule (24 hours, only in `kernel.payment_links`, redacted from the access log); facts name the `link_id`; a visitor sees the token only in the card's `href` (`href_for`).
- **Claude never sees server text.** Every MCP tool carries the adapter's `description_confirmed` and `input_schema`; the server's description reaches only the owner, as quoted untrusted `pending_definition_text`; charge titles come from kernel data, never the server.
- **Clients:** the MCP client builds `mcp.Client(..., cache=None)` (the v2 SDK caches `tools/list` by default, which would hide drift) over `streamable_http_client(url, http_client=httpx2.AsyncClient(headers=..., trust_env=False))`, fresh per call, with `X-Mockpay-Key` and `X-Desk-Copy`; `ProviderClient` also sets `trust_env=False`. Provider bodies and MCP results parse through `strict=True, extra="forbid"` models with money as `StrictInt` in 0..1_000_000.
- **Tests** run the mock server in-thread on an ephemeral port (a session fixture in `tests/kernel/conftest.py`, passed to `create_app`) and the fetch on an injected resolver and `httpx2.MockTransport`: no money, no network. Test hooks (the delay switch) answer 404 with `DESK_ENV=production`.
- **The Desk's money cap** (Plan 01b's Task 3b; master "Money cap"). The cap is a field of each rules version, and the Desk's cap is its active version's. A Desk made with `POST /desks` starts at a cap of 0, so a test that drafts an auto money card on one sets its cap first, through `draft_and_confirm(..., auto_money_cap_cents=50_000)`; Turner copies start at $500, so `rv-link` ($300), `rv-mandate` ($20) and Plan 05a's money rows keep their numbers. Task 4's `/tools/confirm` draft is at the active version's cap, which the active cards it carries already fit. A confirmed rule or cap change cancels, in its activation's transaction, the open auto-allowed payment links the new version no longer allows (Task 3), and a link being issued as it activates is checked against the new version before it opens (Task 2); completion rechecks only the baseline (Task 3).
- **Owner-facing text** (drift alerts, probe `reason_plain`) is plain, with no Cedar, MCP or policy words.
- **Evals gate** (master "Evals gate"): tier 1 rows are `requires("01c")` for Tasks 0–7 and `requires("01c-setup")` for Tasks 8–9; `01c` joins `evals/tier1/landed.toml` with Tasks 0–7, `01c-setup` with Tasks 8–9; the PR gated by the money and agent rows; tier 2 as Task 10 says.

## What this plan serves

- The acting is real: a visitor pays at a labelled test checkout and sees it confirmed in the chat; a verified customer sees and refunds their own charges; another person's agent pays within its signed limit and no further.

### Task 0: Withhold, never fail, what an adapter outside the kernel already did

Before any adapter that acts outside the kernel (the mock payments server's tools, an MCP refund), kernel verification's private data guard and its private recovery change shape, since recording such an action as not run would be false: a charge or refund that went through would read as never made, and its mandate reservation would be released. It lands in PR 1, before Task 2's payment links, the first adapter that acts outside the kernel.

**Files:**
- Modify: `backend/desk/kernel_service/execute.py` (`_visible`, `_ask_adapter`, `_refused_in_recovery`; `UndeclaredPrivateData` goes, since nothing raises it), `backend/desk/kernel_service/adapters/__init__.py` (`_check`)
- Modify: `backend/tests/kernel/fakes.py` (`FakeAdapter(releases_private_data=True)` adds the `private_data` effect to its profile, so the stand-ins that declare it still register)
- Test: `backend/tests/kernel/test_private_release.py`

**Interfaces:**
- The guard (`undeclared_private_data`, unchanged): `_visible` no longer raises. A result it refuses is withheld: the stored and returned result has no facts, an empty `model_view` and no inbox notices, and the `execute` entry adds `{violation: "undeclared_private_data"}`, beside the canary's `{violation: "canary"}`. The log line stays `adapter_undeclared_private_data tool=<tool> action_id=<id>`, never the data. The decision is `executed` and the execution `succeeded`; no `on_failed` runs; the adapter's own writes stay (they record what it did outside the kernel), except that every fact row named by the refused result's facts is narrowed, in the same transaction, to the owner (`readers` `["owner"]`, the fact rows' default; `record_owner` kept). A misdeclared adapter is exactly one whose labels can't be trusted, so the session's later reads must not rest on them. The entry records how many rows were narrowed (`narrowed: <count>`, beside the violation), so the owner can tell why a fact they see wasn't delivered. The guard reads only the facts an adapter returns, so a row an adapter writes without returning it isn't narrowed: that is acceptable only because kernel-side adapters are reviewed code and MCP adapters can't write kernel rows, and it means the guard is not a sandbox for adapter code. The visitor's status line is the `executed` state's own, as for a canary-withheld view. This holds on T2's allow and approved paths alike.
- Reconciliation of an orphan whose session still stands (`_ask_adapter`), three outcomes: a result → `executed`, through `_visible`, so a result the guard refuses is withheld as above (its fact rows narrowed to the owner), the violation on the reconciled entry, with no `on_failed`; None → `failed` after `on_failed`, as now; an error (`AdapterUnknown` or any other) → still `unknown`, with whatever `reconcile` wrote taken back, for the next read, as now.
- A private action's orphan whose session no longer stands (`_refused_in_recovery`) asks the adapter first and delivers nothing whatever it answers, under the session row it already holds: a result → `executed` with the empty result, the entry `{reconciled: true, withheld: "session_ended", check: <why>}`, no `on_failed`; None → `on_failed`, then `refused_at_execution` as now (`reason: "session_ended"`, the `check`, nothing in its result); an error → still `unknown`, nothing delivered, for the next try. `on_failed` runs before anything is ledgered (the lock order in `repo.py`), and a failing `on_failed` leaves the action `unknown`, as now. The visitor's line is the state's own, never why the session ended.
- Registration (`adapters.register` → `_check`): an adapter whose `releases_private_data` differs from `"private_data" in profile.effects` raises `ValueError` naming the tool. Every adapter registered today agrees, native and MCP alike.
