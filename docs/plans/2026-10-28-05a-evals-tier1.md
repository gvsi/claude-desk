# Claude Desk Prototype — Plan 05a: Evals tier 1

> **For agentic workers:** Execute with the repo's `executing-implementation-plans` skill (`.agents/skills/`): a fresh implementer and a task review per task, in the plan's worktree, landing through one PR after the review panel. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A model-free tier 1 suite that runs on every commit: the kernel's boundary cases replayed through its HTTP contract and, once Plan 02a lands, through the API, each call stating its expected response and judged by oracles that never import what they judge. It lands Thursday morning and gates every kernel PR from Plan 01a's on.

**Architecture:** `evals/` is a Python package in the backend's uv environment (group `evals`). Cases are pytest tests against `KERNEL_ROUTES`. They run against a contract stub until the kernel plan they need lands, then against the real kernel in-process (`KernelTarget`), with model calls answered by a local fake Anthropic server and time on a travelling clock. API cases run on an `ApiTarget`, an interface this plan defines and Plan 02a implements. Plan 05b (`docs/plans/2026-10-28-05b-evals-tier2-and-report.md`) builds tier 2, the gate and the report on this harness.

**Tech Stack:** Python 3.13 in the backend's uv project (group `evals`): pytest, pytest-asyncio, `httpx==0.28.1`, `httpx-sse==0.4.3`, `pyyaml==6.0.3`, `polyfactory==3.3.0`, `rfc8785==0.1.4`, `cryptography==50.0.2`; uvicorn, Starlette and `anthropic` at the backend's pins. References: [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785); Messages API [streaming](https://platform.claude.com/docs/en/build-with-claude/streaming).

**Spec / master plan:** `docs/specs/2026-10-28-claude-desk-design.md` ("Enforcement (locked)"); `docs/plans/2026-10-28-00-master-plan.md` ("Evals gate (Plan 05)", "Shared seams", "Review Focus", "Kernel HTTP API v2", "Session state responses", "Shared contracts v2", "Turner seed", "Data model and database roles", "Fail-closed behavior", "Schedule, lanes and gates").

## Global Constraints

The master plan's "Global Constraints" apply as written; these cases exercise most the trust-boundary, decision, reply and always-on baseline lines. Specific to Plans 05a and 05b (05b adds its own):

- **Oracles are independent of what they judge.** Pass/fail never comes from the kernel's reply check, lexicons, renderers, compiler, reference generator or `decide`; ledger and signature checks use `evals/oracles/` (`rfc8785`, `cryptography`), cross-checked against `desk_kernel.verify_chain`. Kernel records are evidence, never a verdict.
- **A miss is never fixed by moving the goalposts.** Failing cases are fixed in the product; a case that contradicts the master plan goes to the project owner. Thresholds and recorded rates change only through Plan 05b's calibration and record steps, with the report and reason in the same commit; 05b's `results-check` enforces what CI can.
- **Fail closed.** An errored or timed-out case fails. Tier 1 skips a case only when a plan it `requires` hasn't landed (`pending <plan>`), when it needs the API (`needs api`) or kernel code (`needs kernel code`) on the stub, and lists every skip. Stub results are reported as "contract-checked", never as passes.
- **Tier 1 makes no model calls.** The conftest loads only database URLs from `.env`, sets `ANTHROPIC_API_KEY=tier1-dummy` and `ANTHROPIC_BASE_URL` to the fake for the whole process, and refuses any socket connection off loopback; an unscripted model call fails the test.
- **The Demo inbox is out of the attacker's reach** ("Demo limit: the Demo inbox"). The harness reads a session's own inbox only where a test or scenario declares the verification it plays (a tier 1 legitimate verification; tier 2's `verify_as` or `verify_on_prompt`, set up before the simulator's first turn), never on a simulated visitor's request.
- **No secrets, codes, tokens or keys in artifacts.** Transcripts and reports carry `<code>`, `<token>` and `<key>` in their place after the run is judged in memory; `FakeAnthropic` never stores `x-api-key` or `authorization`.
- **This plan's evals gate:** it changes no kernel code, prompt or policy; every task runs `make evals-tier1`. Nothing deploys from this plan.

## What this plan serves

- Every commit replays the ways a stranger, an agent or a buggy API could push the kernel: forged and stale credentials, another copy's records, pushed discounts, spelled-out prices, wrong-person documents, replayed approvals, restarts mid-payment.
- Each kernel plan merges only when its own cases pass, so "can't be talked around" holds from the first kernel PR.
- A first-time visitor never sees the suite; it is why a pushed discount reliably holds and a price never shows up in prose.
