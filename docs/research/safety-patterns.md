# Claude Desk: runtime policy enforcement, design patterns and production practice

Research date: 2026-10-28

Background research for the Claude Desk design; claims are cited, and anything not confirmed from a source is marked UNVERIFIED.

Scope: how to enforce an owner's plain-language charter on a public, always-on agent whose main adversary is the person in the conversation. Claims I could not confirm from a primary source are marked **UNVERIFIED**. A few findings are carried over from earlier research; each is cross-referenced to the file in `docs/research/` that sources it, or marked **UNVERIFIED** where no source is given here.

## 0. The core problem in one paragraph

Nearly all published system-level defenses against prompt injection assume the user is trusted and the attacker hides in tool output: CaMeL says "We assume that the user prompt is trusted" ([arXiv 2503.18813](https://arxiv.org/html/2503.18813)), and Progent says "we assume the user 𝒰 is benign, and as such, the user's input query is always benign" ([arXiv 2504.11703](https://arxiv.org/html/2504.11703)). In Claude Desk the stranger *is* the user, so these defenses do not apply as published. The design-pattern paper names the consumer chatbot case directly: "Since the chatbot is consumer-facing, the main risk we consider here are prompt injection attacks in the user's prompt" ([arXiv 2506.08837](https://arxiv.org/html/2506.08837)). The practical move is to **re-frame**. The *owner's charter* becomes the trusted "user prompt". The *visitor's text* is treated like an untrusted tool result: read by a quarantined component and turned into typed, bounded data before anything privileged sees it. Every action and every commitment in the outgoing reply must then pass a deterministic check against the charter and the visitor's verified identity.

## 1. Patterns and papers

| Pattern / system | Mechanism | Defends against | Cost | Handles a hostile USER turn? |
|---|---|---|---|---|
| **Action-selector** ([Beurer-Kellner et al. 2025](https://arxiv.org/html/2506.08837)) | LLM only maps a request to a fixed menu of actions; tool output never returns to the LLM | Injection steering actions | Agent can do only what the menu allows | **Partly yes**: the paper says it "can also be effective against prompt injections in the user input" when the prompt is dropped before the reply. The attacker can still pick any allowed action, so the allowlist itself is the policy. |
| **Plan-then-execute** | Commit to a tool-call plan before reading untrusted data | Tool output altering which actions run | Tasks with data-dependent steps are hard | **No**: "this pattern does not prevent prompt injections contained in the user prompt." |

| **Dual LLM** (Willison 2023; formalised in the paper) | Privileged LLM plans and calls tools and never sees untrusted text. Quarantined LLM reads untrusted text, has no tools, and returns symbolic or typed outputs | Untrusted text reaching the tool-calling model | Two calls, plus plumbing for symbolic variables | **Yes, if the visitor's message is routed to the quarantined side**. This is the re-frame in §0. |
| **Code-then-execute / CaMeL** ([Debenedetti et al., Google DeepMind + ETH](https://arxiv.org/html/2503.18813)) | P-LLM writes a Python plan from the trusted query. Q-LLM parses untrusted data into schemas. A custom interpreter tracks capabilities (provenance, allowed readers) and checks each tool call against Python policy functions | Data-flow and control-flow hijack via tool output; exfiltration to unauthorised readers | 77% of AgentDojo tasks solved securely vs 84% undefended. About **2.82x input / 2.73x output tokens** vs native tool calling. Policies must be written and maintained. User-confirmation fatigue. Vulnerable to side channels | **No as published** (trusted-query assumption). Its capability tags are still exactly what Claude Desk needs for "this document may only be read by verified person X". |
| **Context-minimization** | Remove the user's prompt from context after it has selected an action, so it cannot shape the final reply | User-turn injection shaping the *response* (the paper's car-discount example) | Reply cannot react to the user's wording | **Yes**: "the user's prompt is removed from the context, thereby preventing the prompt injection." This is the paper's fix for the "large discount" attack. |
| **FIDES** ([Costa et al., Microsoft, 2505.23643](https://arxiv.org/abs/2505.23643)) | Planner with dynamic taint tracking. Confidentiality and integrity labels on every value, deterministic policy enforcement, primitives to hide labelled values from the model | Exfiltration (confidentiality) and untrusted data driving actions (integrity) | The abstract does not quantify utility loss. The paper includes a task taxonomy of what IFC can and cannot do | **Indirectly**: if visitor text is labelled low-integrity, it cannot drive high-integrity sinks such as payments or document release. |
| **Progent** ([Shi et al., Berkeley](https://arxiv.org/html/2504.11703)) | Symbolic allow/deny rules over tool names and arguments, enforced deterministically. An LLM may propose policy updates, and an SMT check auto-applies only narrowing updates ("monotonic confinement"). Expansions need approval | Tool misuse via injection | AgentDojo ASR 39.9% to 1.0% with utility maintained. ASB 70.3% to 3.9%. Manual policies "can provably reduce the ASR to 0%". An adaptive black-box attack on Progent did not raise success (25.8% to 4.2% mean, [arXiv 2606.26479](https://arxiv.org/abs/2606.26479); weak 7B model, white-box attacks untested) | Assumes a benign user. The **mechanism is user-agnostic**, though: a rule like `refund.amount <= charter.max_refund` blocks the call no matter who asked. |
| **ActGov** ([2609.24446](https://arxiv.org/abs/2609.24446), Sep 2026) | Task-scoped authorization boundary plus SMT-checked policies built from tool specs and failure traces | Indirect injection | The abstract claims utility is preserved; numbers not checked | Not stated (indirect-injection focus). |
| **Meta Agents Rule of Two** ([Meta, 31 Oct 2025](https://ai.meta.com/blog/practical-ai-agent-security/)) | Within one session an agent should have at most two of: [A] untrusted input, [B] sensitive systems/private data, [C] change state or communicate externally. With all three it "should not be permitted to operate autonomously" and needs human-in-the-loop "or another reliable means of validation" | Severity of any successful injection | Lost autonomy, or narrower sessions | It is a **session-design rule, not a detector**. Claude Desk is always [A]. A session may therefore hold [B] *or* [C] autonomously, not both. Willison noted that [A]+[C] alone is "lower risk", not "safe" (Meta changed its label after his critique: [Willison, 2 Nov 2025](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). Meta says it is not "a finish line" and does not cover agent mistakes or hallucinations. |
| **Lethal trifecta** ([Willison, 16 Jun 2025](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)) | Private data + untrusted content + external communication means an attacker "can easily trick it into accessing your private data and sending it to that attacker" | A framing for exfiltration risk | — | Claude Desk has all three by design. In Claude Desk the reply to the stranger is itself the exfiltration channel. |
| **Separate checker that never sees raw untrusted text** | Examples: Chrome's **User Alignment Critic** "architected to see only metadata about the proposed action" and able to veto ([Google, 8 Dec 2025](https://blog.google/security/architecting-security-for-agentic/)). Claude Code **auto mode** classifier "sees only user messages and the agent's tool calls", with Claude's messages and tool outputs stripped ("reasoning-blind by design"); two stages, FPR 8.5% to 0.4%, **17% false-negative rate on real overeager actions**; stops after 3 consecutive or 20 total denials ([Anthropic, 25 Mar 2026](https://www.anthropic.com/engineering/claude-code-auto-mode)) | Actions that drift from the principal's intent | One extra model call per action. Two-stage design keeps it cheap | **Caution**: auto mode's critic deliberately *does* read user messages, because in Claude Code the user is trusted. For Claude Desk the critic must read the **owner's charter + typed action + verified identity**, never the visitor's raw text. |
| **Chain-of-thought auditor that does see the trace** (LlamaFirewall AlignmentCheck, [arXiv 2505.03574](https://arxiv.org/html/2505.03574v1)) | LLM audits the agent's reasoning for goal drift | Indirect injection | AgentDojo ASR 17.63% to 2.89% (with PromptGuard 2: 1.75%). Utility 47.7% to 42.7%. About 0.9-1.5 s per step in one example trace | Authors warn "AlignmentCheck itself can be targeted by prompt injections designed to manipulate both the agent and guardrail LLM", and that it needs large models. **Do not rely on it against a user who can write directly into the trace.** |
| **Input classifiers** (PromptGuard 2: 97.5% recall @1% FPR, 92 ms (86M) / 88.7%, 19 ms (22M); Model Armor; Claude Haiku "harmlessness screen" per [Anthropic docs](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)) | Classify the user turn before the main model sees it | Known jailbreak and injection patterns | Low latency, but false positives on legitimate customers | Helpful as a tripwire and for "repeat offender" throttling. "The Attacker Moves Second" broke 12 in-band defenses at >90% with adaptive attacks, and human red-teamers succeeded on 100% ([arXiv 2510.09023](https://arxiv.org/html/2510.09023)), so a classifier is **not** a boundary. |
| **Output / commitment verification** | (a) Deterministic quoting: the LLM cites IDs and code substitutes the verbatim text ([Willison on Yeung, May 2024](https://blog.simonwillison.net/2024/May/7/deterministic-quoting/)). (b) AWS Bedrock **Automated Reasoning checks**: natural-language policy compiled to logic, responses checked Valid/Invalid/Satisfiable, "up to 99% verification accuracy" (vendor claim; [AWS, 6 Aug 2025](https://aws.amazon.com/blogs/aws/minimize-ai-hallucinations-and-deliver-up-to-99-verification-accuracy-with-automated-reasoning-checks-now-available/)); no latency figures; does not mention injection. (c) Output rails (NeMo Guardrails, Model Armor after-model callback, OpenAI Agents SDK output guardrails/tripwires) | Invented prices, policies or discounts (Air Canada, Cursor "Sam", Chevy $1) and leaked sensitive strings | Extra pass on every reply. False positives on paraphrase | **Yes for outcomes**: the check runs on the outgoing text and does not care who caused it. I found **no published named pattern** for "a reply may only contain a commitment that a tool issued". It is a synthesis of deterministic quoting and CaMeL capabilities, proposed below. |
| **Capability scoping per session/identity** | Least privilege per principal. Example: Google's secure customer-service codelab gives the agent its own IAM identity and denies the admin dataset ("Any attempt to query admin.audit_log will be denied by IAM"), but the grant is dataset-wide, with **no row-level or per-customer authorization** ([codelab](https://codelabs.developers.google.com/secure-customer-service-agent/instructions)) | Agent reaching data or tools it should not have | Engineering effort | **Yes, the strongest user-agnostic control**, provided scoping is per *visitor* (e.g. a session token bound to verified identity), not per *agent*. The codelab's gap is exactly the Claude Desk failure mode. |

**Takeaways for Claude Desk**

1. The defenses that survive a hostile user are the ones that **don't ask the model to notice the attack**: deterministic tool-argument policies (Progent/ActGov style), per-visitor capability tokens, information-flow labels, context minimization, and output checks on commitments. Scammer4U found agents that *flagged* a site as suspicious still leaked PII 35.9% of the time (carried over from earlier research, **UNVERIFIED** here), so detection is the wrong gate.
2. Guard models are useful as tripwires and for triage. None of them is a boundary. Adaptive and human attackers break in-band detectors (2510.09023, 2408.15221), and a checker that reads the attacker's text can itself be injected (LlamaFirewall C.4).
3. Expect a utility tax: CaMeL 84% to 77%, AlignmentCheck 47.7% to 43.1%, plus roughly 2.8x tokens for full CaMeL. Claude Desk must log legitimate-request completion alongside attack success.
4. Customer-service-specific red-teaming exists: CRAFT/τ-break uses policy-aware persuasion, reached 70% ASR in the airline domain, and found that simple defenses "fall short" ([EMNLP 2025](https://aclanthology.org/2025.emnlp-main.114), [arXiv 2506.09600](https://arxiv.org/pdf/2506.09600)). Use τ-break-style suites as the Claude Desk eval.

## 3. Human-in-the-loop design

**Evidence on approval fatigue**
- Anthropic: manual prompts lead to "approval fatigue, where people stop paying close attention", and "in practice users accept 93% of them anyway" ([auto mode, Mar 2026](https://www.anthropic.com/engineering/claude-code-auto-mode)). Secondary reports of 97% approval, and of humans catching 13.6% of planted dangerous commands vs the classifier's 89%, are **UNVERIFIED**.
- Sandboxing cut permission prompts by 84% internally ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)). Bounding the blast radius reduces how many decisions need a human.
- Trust accumulates: auto-approve use rises from about 20% of sessions (<50 sessions) to over 40% (750+), and interrupts rise from 5% to 9% of turns. "Effective oversight doesn't require approving every action but being in a position to intervene when it matters" ([Anthropic, 18 Feb 2026](https://www.anthropic.com/research/measuring-agent-autonomy)).
- CaMeL lists user fatigue from frequent confirmations as a limitation. Meta notes a user "might blindly confirm a warning".
- Unit 42 (retail fraud): an approval UI that shows only a **total** let an injected gift card through (carried over from earlier research, **UNVERIFIED** here). **Approvals must show the specific itemised effect.** OAuth Rich Authorization Requests exist for this: Auth0's async authorization (CIBA + RAR) shows amount and payee on the approver's device, and the tool runs only after approval ([Auth0](https://auth0.com/ai/docs/intro/asynchronous-authorization)).

**Design rules distilled**

1. **Gate by consequence, not by frequency.** Ask the owner only for irreversible or above-limit actions: money over the charter cap, first release of a sensitive document, new commitments outside the charter. Everything else is either auto-allowed by rule or auto-denied.
2. **Async approvals.** The visitor hears "I've asked [owner]; you'll get a reply by email/SMS". The conversation does not block. The approval request is a structured card (who, verified how, what exactly, which charter rule it would exceed, one tap: *Allow once / Always allow for this person / Always allow this kind / Deny / Deny & block*). The MCP elicitation accept/decline/cancel model and Claude Duet's approve-before-send behaviour are existing building blocks (Duet: see `safety-anthropic.md`; the MCP elicitation model is **UNVERIFIED** here).
3. **"Allow once / always" semantics.** Android's "Only this time" is a one-time grant, and unused permissions auto-reset after months ([Android 11](https://developer.android.com/about/versions/11/privacy/permissions)). For Claude Desk, "Always" should be **scoped** (this verified person, this action type, this cap) and **expiring** (e.g. 90 days), and should be stored as a deterministic rule the owner can read in plain English. "Deny always" should beat everything, as in the Claude Agent SDK where deny rules override hooks and modes (see `safety-anthropic.md`).
4. **Graduated autonomy that only narrows automatically.** Borrow Progent's "monotonic confinement": the system may tighten rules on its own (e.g. after a suspicious conversation), but any widening needs an owner tap. Offer "suggested rule" nudges after N identical approvals, e.g. "You've approved 5 refunds under $20 for verified repeat customers. Make that automatic?". Track override rate: near-zero denials suggests rubber-stamping (practitioner heuristic, **UNVERIFIED** as a measured result).
5. **Circuit breakers.** Following auto mode's "3 consecutive denials or 20 total": a visitor session that trips N blocks gets downgraded (no tools, FAQ-only, or handed to the owner), and the anonymous identifier is throttled, as Anthropic's docs suggest for repeat offenders.
6. **For non-technical owners:** charter rules are shown as sentences ("Never give more than 10% off", "Only send the lease to the tenant on file after they verify by text"). Each sentence is backed by a compiled check whose status is visible (enforced by code / enforced by AI judgment / not enforceable, needs approval). Being honest about which rules are hard and which are soft is the key UX point.

## 5. A Claude Desk-specific synthesis: the "commitment ledger"

Two failure modes need different primitives:

- **Bad tool calls** are handled by deterministic gates on arguments (Progent/ActGov style), keyed to the session's verified identity and the compiled charter.
- **Bad outgoing messages** are handled by making every *commitment* in a reply a reference to a ledger entry that a tool created. Price, discount, refund, appointment slot, delivery date and "document sent" are only valid if `quote_tool` / `booking_tool` / `release_tool` issued them inside charter limits. The reply generator emits structured output (`text` + `commitments: [ledger_id…]`). A deterministic checker then (a) confirms every ledger ID exists, belongs to this session, and is within limits; (b) scans the text for commitment-shaped spans (currency, %, dates, "free", "refund", "guarantee", "binding") and rejects any not backed by a cited ID. Optionally an Automated-Reasoning-style or LLM claim-extractor pass runs on policy statements, comparing them to charter text, with a deterministic quote substituted for paraphrase (Willison/Yeung). For leakage: private-document content enters the reply model's context only through a capability-tagged read that the session is entitled to, and an output DLP pass checks for spans of documents the session is *not* entitled to (canary strings/hashes per document make this deterministic).

This is not a published, named pattern (my synthesis). It is the direct answer to Air Canada, Chevy, Cursor and "leaked document".

## Candidate architectures for Claude Desk

Latency and cost figures below are engineering estimates, **UNVERIFIED**, derived from the CaMeL token multiplier, PromptGuard/AlignmentCheck timings and auto mode's two-stage design.

### A. "Shell and gates" (single agent, deterministic perimeter). The v1 baseline

Layers:
1. **Edge**: rate limiting, identity tier (anonymous / contact-verified / known-party), PromptGuard-class or Haiku input tripwire. *Sees* raw visitor text. *Blocks* known attack patterns and repeat offenders, and downgrades the session. Not trusted as a boundary.
2. **Main agent (Opus/Sonnet)**: sees charter, visitor text, and only the data the session's capability token allows (public KB plus this verified person's records). *Proposes* tool calls and replies.
3. **Tool gate (code, e.g. Agent SDK PreToolUse hook)**: sees typed tool call + session identity + compiled charter. *Blocks* out-of-scope tools, arguments over limits, document release to non-entitled identities, and identity/contact changes that are not verified out of band. Escalates over-cap calls to async owner approval.
4. **Reply gate (commitment ledger + DLP)**: sees the outgoing text + cited ledger IDs. *Blocks* unbacked prices, discounts or policies and non-entitled document spans; rewrites to a safe fallback ("Let me check with [owner]").
5. **Owner loop**: async approval cards, daily digest, attack ledger.

Cost/latency: about 1.1-1.3x a plain agent. The gates are milliseconds of code; the input screen is roughly 20-100 ms for a small classifier or a short Haiku call. Residual risk: the main model reads hostile text *and* holds the session's private data, so within its entitlement it can be talked into saying things in free text that the reply gate does not recognise as commitments (soft promises, tone, mis-stated policy paraphrase), or into leaking entitled-but-sensitive data to the right person through a social-engineering frame. Every gate depends on the charter being compiled correctly.
**Owner explanation:** *"The assistant can chat freely, but a locked checkpoint stops any payment, document or promise that breaks your rules before it goes out."*

### B. "Receptionist and back office" (dual LLM with context minimization). Recommended target

Layers:
1. **Receptionist (quarantined LLM, no tools, no private data)**: sees raw visitor text plus the public KB. Outputs (i) a *typed intent* from a fixed menu (`book(slot_pref)`, `quote(item, qty)`, `request_doc(doc_type)`, `refund(order_ref)`, `question(topic)`, `other`) with bounded slots (enums, IDs, numbers, no free text into privileged fields), and (ii) draft conversational text for public questions.
2. **Back office (privileged planner, CaMeL/FIDES-style)**: *never sees visitor text*. Sees the charter, the typed intent, the identity tier, and owner data. Runs plan-then-execute over tools with capability labels (e.g. this document readable only by the verified principal ID). Tool calls go through the same deterministic gate as A.
3. **Reply composer**: assembles the reply from templates/slots filled by back-office results (ledger IDs, deterministic quotes of charter text), plus the receptionist's public-only prose. The commitment ledger and DLP checks from A run on the final text.
4. **Critic (optional, Chrome-style)**: sees only metadata about the proposed action + charter + identity tier, never visitor text, and can veto.
5. **Owner loop** as in A, with Progent-style monotonic confinement: rules only widen on owner approval.

Cost/latency: about 1.5-3x tokens (CaMeL measured about 2.8x) and an extra 1-3 s per action turn. Pure Q&A turns stay single-model. Utility tax: requests that don't fit the intent menu fall to "I'll pass this to [owner]". Expect a CaMeL-like 5-10 point task-completion drop, to be measured on τ-break-style suites. Residual risk: the attacker controls *which* allowed intent is chosen and its slot values, so the charter must be safe for any allowed intent. The receptionist's free prose can still be manipulated (insults, off-brand content, or the receptionist claiming things), so the reply gate remains necessary. Mislabelled identity or charter-compilation bugs remain, as do side channels (CaMeL notes them).
**Owner explanation:** *"The person at the front desk talks to customers but can't open the safe; the back office can open the safe but only reads the request slip, never the customer's sales pitch."*

### C. "Two kinds of session" (Rule of Two split, with human approval for the trifecta)

Layers:
1. **Public session [A]+[C]**: anonymous or contact-verified. Can answer from the public KB, propose bookings into a *pending* queue, and generate quotes only from the price-list tool. No private documents, no refunds, no payment capture beyond a hosted checkout link at list price.
2. **Verified session [A]+[B]**: entered only after known-party step-up (OTP to the contact on record, RFC 9470-style `max_age`). Can read this person's own records and draft document releases or refunds, but **cannot send or execute**. Outbound effects are queued.
3. **Executor (no LLM in the loop, or a fresh-context agent)**: executes queued items that fall inside auto-allow rules (e.g. "release the lease PDF to the verified tenant", "refund ≤ $25 to the original card"). Everything else goes to the owner's async approval card, showing the itemised effect (CIBA/RAR-style).
4. **Reply gate** (commitment ledger) on both session types.

Cost/latency: cheapest per turn (no dual-model plumbing). Latency shifts to *wall-clock* waits for owner approvals on anything above the auto-allow line. Residual risk: approval fatigue if the auto-allow line is set too low. Rubber-stamped approvals are an attack surface (Unit 42 total-only UI). Auto-allow rules are themselves attackable within their bounds (e.g. many small refunds), which needs velocity caps. A verified-but-malicious known party can still extract their own data and talk the model into unflattering free text.
**Owner explanation:** *"Strangers get the shop window; people who prove who they are get their own folder; anything that moves money or sends a private file beyond your auto-OK rules waits for your thumbs-up."*

### How to choose

- Ship **A** first: smallest build, and it reuses the Agent SDK hooks.
- Move high-value actions to **C**-style queued execution from day one: this is Meta's Rule of Two plus the Meta account-recovery lesson.
- Grow toward **B** for the tool-driving path once the intent menu stabilises, so the stranger's words never reach the model that holds the keys.
- In all three, the two controls that do not depend on the model's judgement are the **tool gate keyed to verified identity** and the **commitment ledger on outgoing text**. Every other layer only reduces how often attacks reach those two controls.
