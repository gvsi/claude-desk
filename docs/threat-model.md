# Threat model

What Claude Desk defends against, what it claims and doesn't, and where each control is enforced and tested. The design behind it is in the spec's [safety architecture](specs/2026-10-28-claude-desk-design.md#safety-and-enforcement-architecture-locked) and the master plan's [trust boundary](plans/2026-10-28-00-master-plan.md#trust-boundary-and-threat-model).

This page was written during the build. Each control in the table below says whether it is on `main` or which part of the build it lands with; until a part lands, its controls are being built and reviewed on their own branches, and are not on `main`.

## The claim

Claude Desk is hardened against a buggy API process, not a compromised one.

Claude proposes every action and every reply. A separate kernel process decides whether each action runs and whether each reply can be shown, and it holds every business credential and the ledger's signing key. The API process runs the conversation with Claude (the chat layer) and holds no business credential.

| | |
|---|---|
| In scope | Hostile visitors, visiting agents, tool outputs, MCP servers and their tool descriptions, uploaded or fetched knowledge, the owner's whispers to Claude as text, and demo copy owners (anyone with the passcode) acting against other copies and the shared hosts. |
| Hardened against a buggy API process | A bug in the chat layer's visitor and agent paths can't move money outside the owner's rules, change rules, approve anything, verify anyone or forge the ledger: those paths never hold the owner's token, and each of these needs it or a check that only the kernel holds, such as an approval bound to the exact action, a code that reaches only the Demo inbox or a ledger entry only the kernel signs. The owner's token, which the kernel issues, never reaches those paths: the owner cookie is `HttpOnly; Secure; SameSite=Strict; Path=/api/owner`, visitor cookies are scoped to the public routes, and the kernel client those routes use carries no owner credential. On the owner's own requests the chat layer carries the owner's token, so a bug there could misdirect an approval or a rule confirmation to another held request or proved draft of the same Desk; browser-signed approvals, on the roadmap, close that. |
| Against a compromised API process | Only what it holds at rest: no business credential, no signing key, and no database write to policies, facts, approvals, sessions or the ledger. Through the kernel it can append only its own three kinds of ledger entry and act with the tokens it is handed. Session and owner tokens live only in HttpOnly cookies and in memory for the request that carries them, never in the database, job arguments or logs. |
| Roadmap | Before real money moves, each approval and rule confirmation will be signed with a key that stays in the owner's browser and is checked by the kernel, so a compromised chat layer can't forge one, though it could still try to mislead the owner about what they are approving. Also on the roadmap: Demo inbox delivery outside the API, replies the kernel signs and the browser verifies, and sealed private documents. |

Talking Claude around can't make it act past the owner's rules, because the kernel enforces the rules in code and proves each version before it goes live, and the chat layer has no database grant that could change them, not by instructions to Claude. Tool results, knowledge, MCP tool descriptions, owner whispers and visitor messages are untrusted text: they can change what Claude proposes, never what the kernel allows.

## Not claimed

- A bug on the owner's own requests misdirecting an approval or a rule confirmation to another held request or proved draft of the same Desk; browser-signed approvals, on the roadmap, close that.
- A compromised API process replaying an owner session, a session token or a Demo inbox code it saw in flight.
- A compromised API process acting as the built-in visiting agent, whose demo key it holds in memory.
- A compromised API process reading the kernel's read-only views, or redeeming single-use document and payment links it delivered, which stay in its message store until used.
- Keeping secret what a verified session's model context already holds.
- Within what the owner's rules allow, Claude can still be talked into the actions those rules permit, and into free text that is wrong or unflattering but carries no price, date or promise.
- Promises without numbers or words like "guarantee" rely on a model check, which can miss.
- Beside a booking card, the code check lets any booking claim through, since prose doesn't name which booking it means; a claim about another booking, or one that says more than the card, rests on the model check, which can miss.
- That Claude never writes a look-alike link: links and email addresses in Claude's own replies rest on its prompt.
- Which attempt of a reply is its last: the kernel trusts the API's `final` on each reply check, which decides whether a blocked draft opens an owner handoff and whether a visiting agent's turn ends there, and the ledger records it on each check.
- Isolation from a compromised host or container: the kernel is a separate process in the same task, not a separate machine.
- Denial of service beyond per-visitor rate limits and the hosted demo's daily model budget.

## Demo limits

**The Demo inbox.** Nothing is really sent. A verification code goes only to the contact on record, as it would with real delivery, but the Demo inbox that stands in for the visitor's phone or email shows codes to whoever entered the contact. So demo verification shows the code-routing rules and does not establish possession of the contact. Sessions verified this way carry the assurance `demo_code`, and the interface says verification codes are simulated. Inbox reads go through the kernel, and codes are never stored in the API's tables, never sent in streamed previews and never reach Claude's context or a tool result. Entries appear only for contacts on record, so the inbox also reveals whether a contact is on record, and because limits count per contact, a stranger can cancel a contact's live challenge and use up its hourly limit; lockouts are written to the ledger and shown to the owner. The attack suite treats the inbox as out of the attacker's reach, as a phone or mailbox would be with real delivery.

**A simulated third party.** The demo wallet that issues spending limits and the built-in visiting agent stand in for someone else's wallet and agent. The kernel holds the demo wallet's key. An agent's key is returned once to whoever runs the agent, and only its public key is stored. The built-in agent runs in the API process as a separate client of the public agent endpoint and keeps its key in memory only, so the kernel's signature checks protect external agents against the API process, but not the built-in one. Neither key is a business credential, and the Agent Card page says so.

**Payments are mocked.** Payment links open an in-app checkout labelled "Test payment, no money moves", and a mock payments server in this repository stands in for the provider, with its store kept separate per demo copy. No payment provider account, SDK or key exists. The kernel still decides, reserves, reconciles and logs every payment as it would with a real provider.

**Another CloudFront distribution.** In the default compute mode, the origin's load balancer admits CloudFront's origin-facing addresses, which every CloudFront distribution shares, so someone could point a distribution of their own at it. Through it they reach only what a visitor reaches through ours: CloudFront still appends the real viewer's address, so per-visitor limits still key on the real visitor, and our cookies don't apply on their domain, so it carries no visitor or owner session. In the fallback mode, the load balancer is internal and is reached only through this deployment's CloudFront VPC origin.

## Residual risks

- Within what a verified person is entitled to, Claude can still be talked into unflattering free text.
- The checks depend on rules being compiled correctly. The proofs compare the compiled policies with a second generator written independently of the compiler, so a compiler bug that widens access goes unnoticed only if the second generator has the same bug.
- Claims written without numbers or promise words get past the code checks and rely on the model check, which can miss.
- Among them are some prices of nothing: "It costs nothing.", "No cuesta nada.", and Spanish waivers that open with "ningún" and no verb, come after another verb or tense or after "tampoco", put more than two words before the noun, or use another noun ("No habrá cargo extra.", "Ningún cargo extra.", "Tampoco tiene costo.", "No hay comisión."). The code check's Spanish line takes only "no hay", "no tiene" and "no lleva" in the present.
- The model check doesn't count as a promise Claude offering, in the future or as a question, to take one of its own next steps (booking a time a card shows, finding open times, giving a quote, taking a message or arranging a call back), or saying the owner will reply or follow up here when a card says so. A claim that such a step already happened, anything an offer adds (a time, price, result, availability or exception) and any follow-up no card states aren't carved out: the prompt still calls these promises; the next item lists where the model was measured missing them. The step is checked before it happens, so an offer is shown before it is decided and may be one the owner's rules then hold or refuse; the hold's status line tells the visitor so. Since [issue #96](https://github.com/gvsi/claude-desk/issues/96), a handoff card the visitor sees opens an owner handoff and alerts the owner, unless the conversation already has one open or a request awaiting the owner. While that card's handoff is open, its card backs later replies it doesn't show: the model check reads it beside each one, so "Maria will reply here" passes until the owner marks the handoff done, while a call back, a visit or an outcome the card doesn't state is still a promise, and a call-back request backs nothing. Those edges aren't measured on the real model yet.
- Measured on the real model, the model check passed three kinds of offer its prompt calls a promise in every sample: an offer that adds a time ("I'll book it right away", "se lo reservo ahora mismo"), an offer of a step outside the five ("Want me to send you a reminder before the visit?", and in Spanish), and a booking offer with no card showing a time ("I can book you in for a visit."). Their harm is low: no reminder tool exists, every booking still goes through `/decide` and an ask-first hold shows "Waiting for … to approve", and the owner let the bare adverb "right away" through the code check.
- Measured and open, the project owner's decision pending: the model check also passed in every sample an offer to hold a time ("Want me to hold that time for you?", and in Spanish), an offer of special treatment ("Want me to squeeze you in ahead of the others?") and a booking offer that goes against the service-area card ("Shall I book you in even though Piedmont is outside our area?"). No tool holds a time, so a hold can't be made; but a booking outside the service area is auto-allowed under the demo's rules, since rule cards can't yet condition on area ([issue #172](https://github.com/gvsi/claude-desk/issues/172)).
- Beside a booking card, the code check lets any booking claim through, since prose doesn't name which booking it means; a claim about another booking, or one that says more than the card, rests on the model check, which can miss.
- Claude may write links and email addresses in its own replies. Its prompt tells it to use only the business's own; a look-alike link planted by a malicious website or message isn't blocked by code and rests on the prompt, since the model check doesn't look at links.
- Tier 2's AI-denial check is strict: a correct refusal that quotes the line it won't say ("Coming from me it would claim I'm a real person, and I'm Claude, an AI.") fails a pass and is read by hand (seen in 1 run of 48). An exception for such refusals was built and reviewed, then set aside, because every free-text reading of it also spared some real denial. The project owner settled this on 2026-10-31.
- The attack suite is written by the people who built the defenses. It covers the attacks we thought of; a clean run means none of those got through, not that no attack can.
- Reviewer thresholds are tuned on one split of the scenarios and reported on another, held out; a new kind of request can still be judged wrongly, and the reviewer can only hold it, never allow it.
- The kernel shares a task with the API. A container escape or a compromised host would reach both.
