# Deploying Claude Desk

Claude Desk runs on AWS in us-west-2 behind one CloudFront address: the web app from S3, and `/api/*` from one Fargate task (arm64) that runs the API and, beside it, the kernel, which holds every credential and listens only inside the task. Two CDK stacks hold it: `DeskData` (network, Postgres, secrets, the one-off admin task) and `DeskApp` (the task, its compute and the CloudFront distribution).

Every command here that creates or changes anything in AWS runs only with the owner's go. The first deploy runs in the owner's own terminal; a redeploy is one command that asks for no account ID or passcode and can also run without a terminal (Redeploys, below).

## Before you deploy

**You need:** the AWS CLI v2 with a profile for the account (`export AWS_PROFILE=<profile>`), Docker with buildx (Docker Desktop), Node 24 and uv. `infra/scripts/deploy.sh` installs the pinned CDK CLI with `npm ci` in `infra/`.

**Passcode for smoke checks:** a full deploy needs either an exported `DESK_PASSCODE` or macOS with the `security` command and an unlocked login Keychain containing `claude-desk-passcode`. The first-deploy commands below use the macOS Keychain. On another host, replace their `security add-generic-password` command with this command in Bash, entering the same passcode you hashed for `desk/passcode-hash`:

```sh
IFS= read -rs DESK_PASSCODE && export DESK_PASSCODE
```

The input is hidden and stays out of shell history. `DESK_PASSCODE` takes precedence over the Keychain; unset it with `unset DESK_PASSCODE` after the deploy. For an unattended redeploy, supply it through the host's secret environment along with `DESK_DEPLOY_ACCOUNT`. `--data-only` needs no passcode.

**Sign-off:** the owner's go for the deploy, CI green on the commit, and a clean preflight. `deploy.sh` runs `infra/scripts/preflight.py` first, which stops the deploy before any change unless:

- the working tree is clean and `HEAD` is on `origin/main` (`--allow-branch` skips only the second check);
- `make evals-results-check` passes against the first commit: while every tier 2 scenario is pending, no results file is needed; once any can run, `HEAD`'s own results file must exist and pass;
- both required owner secrets are set (below);
- the web app builds and checks at `HEAD` (`npm ci`, `npm run build`, `npm run check:build` in `web/`).

**Monthly cost** at AWS list prices for us-west-2 (check the pricing pages before relying on them), 730 hours a month:

The hosted demo's daily model budget is $80 (a UTC day): past it, turns hand off with no model call. Since 31 × $80 is more than $1,000, the monthly limit is the one that binds first.

## First deploy (owner's terminal)

```sh
(cd infra && npm ci && npx cdk bootstrap aws://<account>/us-west-2)
infra/scripts/deploy.sh --data-only                 # DeskData alone, in the account you retype
uv run --project infra python infra/scripts/set_secret.py desk/anthropic-api-key
uv run --project backend python backend/scripts/hash_passcode.py \
  | uv run --project infra python infra/scripts/set_secret.py desk/passcode-hash --stdin
security add-generic-password -s claude-desk-passcode -a "$USER" -w   # macOS; elsewhere export DESK_PASSCODE as above
infra/scripts/deploy.sh
```

`deploy.sh --data-only` asks you to retype the account ID it prints, runs preflight without the owner secrets or the web build, builds and checks the image, deploys `DeskData` alone and stops. `DeskData` creates the two required owner secrets as generated placeholders and the optional `desk/typesafe-api-key` with the fixed non-secret value `unset`. `set_secret.py` reads the key without echo (or the hash from the pipe), writes it and tags it `owner-set=<the version it wrote>`. Preflight requires that version to still be the secret's current one, so a value anything else wrote since, such as CloudFormation generating the placeholder again, stops the deploy until you set it again. It prints the version, never the value. Every other secret is generated by Secrets Manager.

Optional TypeSafe evaluation: leaving `desk/typesafe-api-key` at `unset` keeps Jev off, with no TypeSafe request or Jev log; Sonnet checks replies alone. To enable it, the owner runs `uv run --project infra python infra/scripts/set_secret.py desk/typesafe-api-key` before deploying the app. The kernel reads the key only when a new kernel task starts: a deploy of a new commit, or a forced new deployment of the kernel service; redeploying the same commit doesn't restart it. To confirm Jev is on, a checked reply's ledger entry shows `soft_checks.jev.status`. To turn Jev off, set the secret back to `unset` the same way and start a new kernel task. The key is passed only to the kernel. Preflight does not require this optional secret. See the [TypeSafe data-flow limits](threat-model.md#external-reply-evaluation) before enabling it.

`security add-generic-password` asks for the passcode twice without echo (`-w` goes last) and keeps it in your login Keychain as `claude-desk-passcode`. You store it once: every full deploy reads it from there, before any deploy step, unless `DESK_PASSCODE` is exported, which wins. To change it later, run the same command with `-U`. To export the passcode for one run instead, without echo or shell history, run `IFS= read -rs DESK_PASSCODE && export DESK_PASSCODE` and type it (`IFS=` keeps any space at either end), then `unset DESK_PASSCODE` after the deploy. While your login Keychain is unlocked, any process running as you can read the item without a prompt, through `security` as `deploy.sh` does, agent sessions included. Agents never read it themselves, but that is a rule they follow, not something this setup enforces. The passcode must be printable ASCII with no backslash (letters, digits, spaces and ASCII punctuation other than `\`, nothing accented): `security` hands any other back as hex, which wouldn't sign in. Since hex is itself printable, `deploy.sh` checks how the item is stored instead, with `security find-generic-password -g`, which shows a backslash the same way as those characters. It refuses a passcode that breaks the rule before any deploy step, without showing it. It accepts one answer alone, the line that shows the plain value; any other answer from `security -g` is refused too, since it can't be checked. If `deploy.sh` says it couldn't read the item, check that it's stored and that the login Keychain is unlocked, which it may not be over SSH or from a scheduled job.

`deploy.sh` checks the AWS account (here, you retype the ID it prints), runs preflight, `make image image-check` (both images tagged with the commit, and the app image checked for what it must hold, its proof reports included), `cdk deploy DeskData`, the admin task (migrations, then role passwords) and `cdk deploy DeskApp`, then the smoke checks. It stops at the first failure. At a terminal, `cdk deploy` asks for approval there before any change that broadens IAM permissions or security group access. A first deploy without a custom domain deploys `DeskApp` twice, because the API's public links need the distribution's address, which exists only after the first pass. Everything `deploy.sh` and its steps print also goes to `infra/out/deploy-<UTC time>.log`, `cdk deploy`'s diff and CloudFormation events included; only its stack outputs stay on the terminal alone.

The smoke checks (`infra/scripts/smoke.py`) take about two minutes, mostly the event stream kept open past CloudFront's 60 second origin timeout. They sign in with the passcode, which `deploy.sh` gives to them alone, as `DESK_PASSCODE` in their environment, and never print it; `smoke.py` takes it out of its environment once read, so nothing it starts is given it. They also read the Express load balancer's and the app task's security groups (describe calls only): the only sources these may admit are private addresses and, on the load balancer's 443 alone, CloudFront's prefix list, so any public range fails, on any port and however it is written. As a second signal, the service's own endpoint and the task's public IP must refuse connections from your machine.

## Redeploys

Once the first deploy is done, a redeploy is one line on macOS with the Keychain item, or wherever `DESK_PASSCODE` comes from the host's secret environment; otherwise export it first as above.

```sh
DESK_DEPLOY_ACCOUNT=<account> infra/scripts/deploy.sh
```

It runs the same steps without asking for the account ID or the passcode. Instead of having you retype the account ID, it checks that the AWS credentials are for `DESK_DEPLOY_ACCOUNT` and refuses, deploying nothing, when they're for another account. It can also run without a terminal, which `deploy.sh` refuses when `DESK_DEPLOY_ACCOUNT` isn't set. Without a terminal nobody can answer `cdk deploy`'s approval prompt, so before each `cdk deploy` the log gets that stack's security-relevant changes, from a read-only `cdk diff --security-only`, and the deploy runs with `--require-approval never`. A change that broadens access is then on record in the log, but nothing waits for anyone to approve it. Each stack's diff ends with one line, `deploy: security summary for <stack>:`, saying whether `cdk diff` found a change that broadens IAM permissions or security group access (CDK's own check, the one its approval prompt at a terminal uses), so look for those lines after an unattended deploy; a diff that doesn't say stops the deploy before that stack. At a terminal, `cdk deploy` still asks before such a change.

## Custom domain

The hosted demo's domain is `desk.alcantara.xyz`. CloudFront reads certificates only from ACM in **us-east-1**, so the certificate lives there, validated through DNS. The distribution's address never changes after the first deploy, so the DNS record is set once:

1. Deploy once without a domain. The Desk is served at its `PublicUrl`, `https://<id>.cloudfront.net`.
2. At the DNS provider (Porkbun), add a CNAME from `desk` to that `<id>.cloudfront.net` host. Use an ALIAS record for an apex domain.
3. Export both settings and deploy again:

   ```sh
   export DESK_DOMAIN_NAME=desk.alcantara.xyz
   export DESK_CERTIFICATE_ARN=<the certificate's ARN, from: aws acm list-certificates --region us-east-1 --includes keyTypes=EC_prime256v1,RSA_2048 (without --includes the call lists only RSA 2048 certificates)>
   infra/scripts/deploy.sh
   ```

The distribution then answers for the domain with that certificate, and the API builds every link from `https://desk.alcantara.xyz`. Keep both variables exported for every later deploy: `deploy.sh` refuses to deploy without them once `DeskApp` serves a domain, since that deploy would drop the domain from the distribution. The domain and the certificate ARN come from your shell, never from the repo.

**Fallback.** If Express Mode can't run the task, `deploy.sh --compute alb` serves the same task from an internal load balancer that only CloudFront reaches, through a VPC origin. It needs no domain.

## Migrations

A deploy migrates the database before any new task starts, and during the deploy the old and new tasks run side by side. So each migration must work with the previous release's code. A drop of a column or table ships one deploy after the code stops using it.

## After a deploy

- The log ends with `deploy: done. <commit> serves at <url>`, and `curl -s <url>/api/health` shows `"dev_signing_key": false` and `"proof_mode": "symcc"`.
- The load balancer Express created (linked from the service in the ECS console) has an idle timeout of 300 seconds and appends to `X-Forwarded-For` (the client address the API's rate limits read), and its security groups admit 443 only from the CloudFront prefix list `com.amazonaws.global.cloudfront.origin-facing`.
- Both containers are running and healthy:

  ```sh
  aws ecs describe-tasks --region us-west-2 --cluster desk \
    --tasks "$(aws ecs list-tasks --region us-west-2 --cluster desk --family desk --query 'taskArns[0]' --output text)" \
    --query 'tasks[0].containers[].[name,lastStatus,healthStatus]'
  ```

- Logs are per container in the task's log group (`DeskApp-TaskLogs…`), as `kernel/kernel/<task>` and `api/Main/<task>`: `aws logs tail <group> --log-stream-name-prefix api/ --since 15m`.
- With a custom domain, `aws cloudfront get-distribution --id <DistributionId> --query Distribution.DomainName` gives the host the CNAME points to.

## Rollback and teardown

Express rolls a failed deployment back to the running tasks by itself.

To go back to an earlier release, redeploying its commit works only when no migration has shipped since. Check with `git log --oneline <commit>..origin/main -- backend/alembic/versions/`, which prints nothing in that case. Then check out that commit from `main` (its preflight runs that commit's tier 2 results check: once any scenario can run, it needs its own passing results file) and run `deploy.sh` again.

If it prints a commit, roll forward instead, since that migration may already have run. Migrations are never reversed, and every deploy runs the admin task, which migrates the database to the code's latest revision. When the database is at a revision the earlier commit doesn't have, the admin task stops that deploy before `DeskApp` with `Can't locate revision identified by '<revision>'`. Make a commit on `main` that reverts the code but keeps every migration file, and deploy it through the usual preflight and `deploy.sh`. The rule under Migrations (each one works with the previous release's code) is what lets the reverted code run on the migrated database, so it covers going back to the release just before the migration, no further.

To take everything down:

```sh
cd infra
npx cdk destroy DeskApp
aws rds modify-db-instance --region us-west-2 --no-deletion-protection --apply-immediately \
  --db-instance-identifier "$(aws rds describe-db-instances --region us-west-2 \
    --query "DBInstances[?DBName=='desk'].DBInstanceIdentifier | [0]" --output text)"
npx cdk destroy DeskData
```

Some resources outlive the stacks, so you delete them by hand:

- The secrets `desk/signing-seed` and `desk/mockpay-key`, kept so the ledger's signatures stay verifiable. Creating `DeskData` again fails while they exist, so delete them, or keep them and import them.
- The database's final snapshot (`aws rds describe-db-snapshots --region us-west-2 --snapshot-type manual`).
- The Lambda log groups under `/aws/lambda/DeskData-` and `/aws/lambda/DeskApp-`: three keep logs for two years and two never expire.
- The CDK bootstrap stack `CDKToolkit`, with its asset bucket and image repository, if nothing else in the account uses it.
