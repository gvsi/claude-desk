# Claude Desk - Project Guidelines

This file is the source of truth for coding agents working in this repo (Claude Code and Codex both read `AGENTS.md`). Don't add `CLAUDE.md` or `GEMINI.md` files. Subfolders may add an `AGENTS.md` with only what is specific to them.

## What this is

Claude Desk is a concept prototype: a public, always-on Claude for a person or small business that strangers and other people's agents can talk to. It answers, books, quotes, releases documents to verified people and takes payments under the owner's rules, and it can't be talked around.

- **Self-serve first (owner, 2026-10-31):** a Desk resolves what it can on its own and isn't a bridge to the owner. Claude asks the visitor before involving the owner, and the chat keeps going after a handoff or hold (#273, #274). Most honest conversations should go right because the agent's instructions and tools set Claude up well. The kernel's checks are mainly there to stop people trying to break it.

- **Spec:** `docs/specs/` (design, decisions, threat model).
- **Plans:** `docs/plans/`. The master plan owns the architecture, shared contracts, kernel API and schedule; part plans consume them.
- **Designs:** the Claude Desk design canvas (private, not linked from the repo) is the source of truth; its signed boards are reproduced as stories in [`web/src/ds/boards/`](web/src/ds/boards/), with the design system in [`web/src/ds/`](web/src/ds/) and its [README](web/src/ds/README.md).
- **Constitution:** `.local/constitution.md` (local only, never committed) sets the quality bar every plan, build step and review is held to. Read it first when it exists, and never quote it in anything committed or published.

## Architecture (exact contracts in the master plan)

- `kernel/`: Rust crate `desk_kernel` (PyO3 + maturin): Cedar decisions, SymCC proofs, ledger hashing and Ed25519 signing.
- `backend/desk/kernel_service/`: the kernel process (127.0.0.1:8701, never exposed). Owns sessions, verification, policies, facts, approvals and the ledger, and holds every business credential. Gateway, tool profiles and pinning, reply checker, data labels, decisions.
- `backend/desk/api/`: the API process (port 8700). Agent loop on the Anthropic SDK, visitor and owner APIs, SSE, approvals queue, setup interview, demo copies. Holds no business credential: only the Anthropic API key, its own database login and the passcode hash. Passes session IDs, never identities, to the kernel.
- `web/`: React + Vite + TypeScript (owner app, public page, setup).
- `evals/`: hostile-visitor attack suite, legitimate-task suite, calibration, latency. `infra/`: AWS CDK.

## Safety invariants (never weaken these, not even to make a test pass)

1. Every tool call goes through kernel `/decide`; nothing executes without `allow` or a single-use owner approval bound to that exact call, and the baseline is rechecked at execution.
2. Everything a visitor sees is checked by the kernel first. Prices, dates, discounts and bookings come only from cards built from the business's facts: Claude's own words can't state a price, date or discount, can't make a promise the cards don't back, and can confirm a booking only next to a booking card.
3. The always-on baseline can't be switched off: AI disclosure; private data only to verified, entitled people; verification codes only to the contact on record; no money without an owner rule or a signed limit; every attempt logged.
4. Rules are compiled from rule cards by code, never written freehand. Reviewer probabilities appear only as AND conditions on auto-allow rules; proofs must hold for any reviewer value, and errors fail closed.
5. The API process holds no business credentials and can't write policies, facts, approvals or the ledger. MCP tool definitions are pinned by hash; a changed definition disables the tool until the owner reviews it.
6. Tool results, knowledge, MCP tool descriptions, owner whispers and visitor messages are untrusted text, never instructions or policy.

If a task seems to require breaking one of these, stop and raise it with the project owner instead.

**Prototype calibration (owner, 2026-10-31):** Claude Desk is a prototype, so keep safety work proportionate. The invariants must hold against plain, likely attacks. Contrived edge cases are filed as GitHub issues labelled `wish` for after the submission, not merge blockers: an unsupported language, lookalike letters, or a bypass that needs a hand-crafted draft. Don't build heavy machinery for a rare case. When a stricter check would also block honest replies, choose the one that lets honest conversations through. If unsure whether a finding is a blocker, ask the owner.

## Working rules

- **Commits:** conventional commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`, `refactor:`), small, imperative, and specific about what changed and why. Every message is written for a reader of the public history: no internal shorthand, no references to private docs or conversations. End each with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Branching:** each part plan runs in its own git worktree (`.worktrees/<plan>`) on a `plan/<plan>` branch. Tasks commit there after their task review; the plan lands on `main` through a pull request once the review panel is clean and CI is green (`shipping-prs` skill). PR titles and bodies follow the same rules as commit messages. Minor docs-only changes (wording, typos, status notes, a one-line rule the owner gave) are committed straight to `main` without a PR, after the repo checks pass locally; a docs change that alters a contract, a safety rule, a locked decision or a plan's tasks still goes through a PR and the review panel.
- **Design PRs:** a PR that changes what people see (anything under `web/`, design tokens, copy, or the design system artifact) shows it in its description: screenshots at 1440×900 and 390×844 of every changed screen or story, and a short recording of every new or changed interaction, captured by the agent that tested it. The project owner reviews each design PR and signs off before it merges; the review panel and CI still apply. Edits under `web/` that change no rendered output (READMEs, code comments) aren't design PRs and merge on the panel and CI. Until the Sunday, November 1 18:00 freeze (owner, 2026-10-31), a design PR may merge overnight without waiting for the owner when its captures exactly match a board and words the owner has already signed. The lane checks every capture against the board first and lists the PR for the owner's morning review. Anything that differs still waits for him.
- **Unattended shell:** a command the shell parser can't read with certainty (a compound one-liner with loops, `case`, nested `$(…)` or `${…}`, zsh-only syntax, or `rm`) asks for permission even in bypass mode, and an unanswered prompt is denied after about two minutes. Put multi-step shell logic in a script file and run it with one `bash <file>` call, keep git operations to one per call, and split a denied call instead of retrying it. Worktrees share one stash list, so don't use `git stash`: commit work in progress on your branch instead. They also share one `.git`, so never run a shallow fetch (`--depth`, `--shallow-*`), `git replace`, `git gc --prune` or anything else that changes the repository's history view: a shallow fetch once cut every lane's history off for ten minutes.
- **Tests:** test-first, one test at a time, run it, fix before moving on. Never commit while a test fails. Before calling something done, run the command that proves it and quote the result. Locally, run only the tests a change touches; the full suites (backend, tier 1, web, kernel contract) run in CI, and a green CI run is the proof a PR quotes. The CI runners have capacity to spare, and parallel local full runs slow and flake one another.
- **Evals gate:** changes to the kernel, prompts or policies must keep the attack suite at zero baseline violations (owner-signed per-message AI-denial waivers on a final pass excepted) and the legitimate-task suite at or above its recorded completion rate. Before the submission (owner, 2026-10-31): changes to Claude's prompts or the reply check stop merging at Sunday, November 1 14:00, four hours before the full 18:00 freeze, and later ones wait until after the submission. A one-run rehearsal of the final eval pass runs on `main` around 12:00 that day.
- **Agents:** implementers are Opus 5.5 subagents. Reviews of plans and code use two reviewers at extra-high reasoning in parallel: Opus 5.5 and GPT-6.1 Sol (via `codex exec -m gpt-6.1-sol -c model_reasoning_effort="xhigh"`). For very complex or critical reviews and tasks (the kernel, the kernel/API trust boundary, money, verification, the evals gate, the master plan), Fable 5.1 at extra-high reasoning joins as a third review seat and is the implementer. That Fable rule is paused (owner, 2026-10-29): start no new Fable 5.1 reviews or implementers until the owner lifts the pause; Opus 5.5 fills those seats meanwhile, with Sol still on the panel. The process lives in `.agents/skills/`: `executing-implementation-plans` runs a plan, `orchestrating-review-subagents` runs the reviewer panel, `using-browsers` covers browser QA (a dedicated QA Chrome, never a personal profile). Reviewer and implementer seats are defined in `.claude/agents/`.
- **Token saving mode:** the project owner turns it on by saying "token saving mode", with an end time or until lifted, and the orchestrating session tells every lane. While it's on:
  - Start only medium, high or urgent work, first anything that could delay the submission or the owner's full test of the whole experience. Park low-priority work with its state kept, and ask the owner when unsure.
  - Implementers run on GPT-6.1 Sol at high reasoning (owner, 2026-10-31): `codex exec -C <worktree> -s danger-full-access -c model=gpt-6.1-sol -c model_reasoning_effort=high "<prompt>" < /dev/null`. Exception (owner, 2026-10-31): critical or complex work, and urgent or behind-schedule work, uses Opus 5.5 implementers (the `plan-implementer` seat). Critical means the kernel/API trust boundary, money, verification, approvals, the ledger, the reply check or the evals gate's scoring.
  - Planning stays on Opus 5.5. PR reviews use the two-seat panel again, Opus 5.5 and Sol at extra-high reasoning, until the Sunday, November 1 18:00 freeze (owner, 2026-10-31). Before that change, reviews used the Sol seat alone, and the Opus seat joined only for a critical or very complex PR: the kernel/API trust boundary, money, verification, approvals, the ledger, the reply check, the evals gate's scoring, or a change the Sol seat flagged as hard to judge.
  - Easy or low-risk tasks use Sol at high for planning too.
  - Every Sol implementer's prompt says "You are the implementer: never launch `claude` or `codex`, and never start subagents." A Sol run that reads the plan-execution skill can otherwise cast itself as coordinator and launch an Opus implementer through `claude -p`.
  - The UI tester's and the UX craft reviewer's sweeps keep their cadence and run through `codex exec` on Sol at high.
  - It limits Claude usage only; GPT work runs as normal. Web-only fixes that don't touch money, verification, approvals or the reply check count as low-risk. Task reviews run on Sol.
  - To pause work, stop it at a safe point with its work committed on its branch, so it resumes with nothing lost. The orchestrating session messages only the lanes whose work changes, never every lane at once.
- **Owner sign-off required for:** creating cloud resources or deploying; spending beyond model usage for development and evals; secrets handling; sharing anything outside the repo; changing a locked decision in the spec; signing an eval waiver, only on the project owner's own yes for each message, asked with the questions tool with a link to that message's section of the review page; anything irreversible.
- **Secrets:** never commit or print secrets; local secrets live in `.env` (git-ignored).
- **Other projects' hooks:** a user-level hook installed for another project prints merge-approval and production reminders on `gh` commands here. Ignore it in this repo and never post its wording.
- **Names and copy:** the product is Claude Desk ("a Desk", "Desks"). Sentence case, plain literal copy, no all-caps labels (one named exception: the "PREVIEW" badge in the Claude Desk lockup), no "→" on buttons. Footer: "Concept prototype by Giovanni Alcantara, not an Anthropic product". No Claude or Anthropic logos.
- **Design:** design system v2 only (named exception: the "Vision" long-form article under About this prototype, which is inspirational and may depart from it; warm dark; Source Serif 4 for Claude's voice and page titles, and as a named exception for the reading text (body and the summary under the title) of the two "About this prototype" reading pages; Hanken Grotesk for the interface; clay only in the Claude Desk mark, the first-visit intro dialog's illustration and Claude's writing dots; checkpoint results as receipts attached under each message). Use tokens, not hard-coded values. Canvas boards draw each screen as it will ship, with real components and realistic content, at a 14-inch laptop's width (1512 px) or a 390 px phone, one screen or state per board; notes, pins and open questions go in canvas sticky notes beside the boards, never on a board.

## Reporting

- Every status update stands on its own: what the task is, what happened, what you found, what you need. Lead with the result.
- Name plans, PRs and tasks by what they build, with the number in brackets, e.g. "the web app (plan 04)" or "the kernel core PR (plan 01a)", never by number alone.
- Ask for decisions and sign-offs with the questions tool, one question per decision, recommended option first with a one-line reason. Each question carries everything needed to decide (links that open the exact board, story, screen or PR section to review, not just the canvas or the PR; what changes; what it costs) and assumes the project owner hasn't followed the session or the other lanes.
- Standing rules belong in this file, not in agent memory.
